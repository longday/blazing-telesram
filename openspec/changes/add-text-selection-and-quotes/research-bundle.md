## How the «Цитировать» action works (3.7.4)

1. **Where it is offered.** Two entries, same action: a floating popup next to the selection («Цитировать», «Копировать»; `ui.chunk.js` component at `@1266715`, selection helpers `@1260887`-`@1266400`) and the first group of the message context menu (`QUOTE_SELECTED`, `COPY_SELECTED`; enum `@523963`, group list `@524427`, click handler `@369912`). The menu entry has the label key `common.quote_selected_text` = «Цитировать» (`lang-ru.chunk.js @44643`), and a sibling «Копировать выделенное».
2. **What can be selected.** Only text inside elements carrying a "copyable" attribute (set by two components: the message text and the emoji-only message). The selection must start and end inside the **same message element**; a selection over several messages offers nothing. The popup appears on mouse up (also after Shift+arrows); it closes on a context-menu open or window blur. `isQuoteAllowed` (module `9764`, `ui.chunk.js @1451073`) is: the selection, taken from the document, is not empty after trim, and both ends lie inside the message's element (matched by its chat id and timestamp attributes). **No length test.**
3. **Can quote** (module `76340`, `app.js @1381920`, exported `z5`): the same predicate as «Ответить» (a message with a version, not ephemeral, not a poll, not a call message, a few more message-kind tests I did not resolve, and the chat's rights allow writing), plus one more predicate on the message's chat id that I did not resolve, plus the selection test above.
4. **Two strings are made from the selection** (module `76117`, `ui.chunk.js @387264`, and the serializer `69972`, `app.js @1265061`): `plain`, the selected DOM fragment joined by `\n` per top-level node, `<br>` as `\n`, then only tested non-blank; and `md`, the selection's **HTML converted to markdown by a small hand-written converter and then trimmed** (whole-string `trim`). The converter maps bold, italic, strike, underline, inline code, links, code fences and block quotes to the markup marks of the messenger's markdown (`**`, `__`, `~~`, `++`, a backtick, `[text](url)`, a fence, `> `); `<br>` becomes `\n`; a `<p>` adds one `\n` after its content; a `<div>` adds nothing; a mark moves surrounding whitespace outside; a link whose text equals its address collapses to the bare address; text nodes are copied as they are (no escaping). So for plain text the `md` is the selected text with `\n` for breaks and no leading or trailing whitespace. Two paragraphs separated by a blank line in the source come out separated by **one** `\n` in `md` (derived by reading, not run: it needs a DOM).
5. **The compose state.** `YG` (module `98416`, `app.js @762185`) puts the composer in mode `QUOTE` for the message and stores `selectionForQuote = {plain, md}`. It also reports a statistic `quote_usage_stats` with the quote's length and **how many times the normalised selection occurs inside the normalised original** (lower-cased, whitespace collapsed), which shows the client knows a fragment can occur more than once, and sends **no offset** to tell which. The state is part of the saved draft (`@3997505`).
6. **Send** (`app.js @769400`-`@770016`): the message's `quoteFragment` is `selectionForQuote.md`. In mode `QUOTE` an **empty own text is refused** («Compose is empty»), unlike a reply/forward mode with message keys. The 4096 test applies to the typed text only (below).

### Unknown (1): the shape of the request

The request body is built in the wire module `22832` (`app.js @1231449`, function at `@1238131`; the same function builds a send and an edit: an edit adds `Timestamp`). `Plain` gets exactly these keys: `ChatId`, `CustomPayload`, `PayloadId`, `MentionedUserIds`, `ForwardedMessageRefs`, `ForwardedMessageStyles`, `UrlPreviewDisabled`, `IsImportant`, `Timestamp` (edit only), and the body (`Text.MessageText`, `Image`, …).

- `ForwardedMessageRefs`: `[{ChatId, Timestamp}]` of the **whole original**. A `ForwardAccessPoint` key appears only for forwards that carry one (from channels) and in one thread special case (a quote in a thread chat whose parent message is the single data-less ref and has an inner message with data: the ref is rewritten to the inner message and the outer one goes into `ForwardAccessPoint`). Neither applies to a quote in an ordinary chat.
- `ForwardedMessageStyles`: one entry per ref; for a single ref the entry is `{Quote: <md string>}` when there is a fragment, or **`{}` (an empty object) when the reply has no fragment**. **No other key**: no offset, no length, no flag, nothing in `Plain` besides the list above. The reader (`@1244336`) likewise reads only `.Quote` from a style entry; for several refs each entry belongs to the ref of the same index.
- So the answer to (1): **a fragment quote is just a string in `Quote`; the original stays referenced by the ref; nothing else is sent.** The string is the markdown of the selection (not the plain text); for text without formatting the two are equal.
- **3.6.3 difference:** the writer had a third boolean parameter; with it false, a reply without a fragment sent an **empty list** `[]` and a fragment `[{Quote}]`; with it true, the same per-ref entries as 3.7.4 (I did not trace which callers pass which value). 3.7.4 has no parameter: always one entry per ref, `{}` for a plain reply.
- **What this means for the app.** The app writes `{Quote: <first 200 characters>}` for **every** reply (`write.rs`), the web client writes `{}` for a plain reply. The web client's reader treats **any** `Quote` string as a fragment quote (it sets `quoteFragment` and renders the multi-line block with the quote icon, below). So a whole-message reply of this app is very probably shown in the web client as a quote block of up to 7 lines rather than a one-line preview. **[INFERENCE]**: derived from the reader code, not seen in a real client; the live check belongs to 0.6, and the answer decides whether D9's rule "a whole-message reply carries a `Quote`" should change to "no `Quote`" (an empty style entry `{}` is what the web client sends).

### The quote length limit, newline and trim handling

- **Length.** The web client applies **no limit to the quote**: not in the selection test, not in the send path. The Russian locale has a string «Цитировать можно не больше {value} символов» (key `plural_quote_max_length_warning`, `lang-ru.chunk.js @44044`; present in 3.6.3 and 3.7.4), but **no code in any chunk of either build refers to it**, so it is dead text and gives no number. The only length rule in the page is the config `messageLengthLimit` = **4096** (page config), applied to the **typed text** of the message (with the long-message flag a longer text is split into chunks of that size, with a hard cap of 40 000; without it the send is refused with «Сообщение слишком длинное»). A quote lies in one message of at most 4096 characters, plus markdown marks, so the web client can send a quote of several thousand characters. Whether the server accepts or cuts it is **unknown from the bundle** (that is unknown (4), for 0.3 and 0.6). The app's `QUOTE_MAX_CHARS = 200` is therefore the app's old bound ("the reference's bound", `write.rs`), not a rule the web client enforces.
- **Newlines.** The selection keeps `\n` (a `<br>` and a paragraph end become `\n`); the converter and the renderer use `\n` only, no `\r`. In the wire string the `\n` is kept as a plain character of the JSON string. When read, the quote is parsed as markdown (below), so a single `\n` inside a paragraph is a soft break shown as a line break (`white-space: pre-wrap`), and a blank line separates paragraphs.
- **Trim.** `md` is trimmed at both ends (all JS whitespace) after conversion; `plain` is not trimmed, only tested for non-blank. No collapsing of inner whitespace, no normalisation of Unicode. (Unknown (3), what the server stores, stays for 0.3 and 0.6.)

## Unknown (6): how a fragment quote is rendered

The reply block of a message (module `88183`, `ui.chunk.js` about `@1437000`-`@1440300`; description module `73265`, `ui.chunk.js @1489699`; styles in `ui.css`, rules `.yamb-message-reply*` at `@2790696`-`@2795698`):

- A reply is the same block for both kinds: the **author of the original** as the title, the text below, inside the rounded background block above the message. The block is clickable (cursor pointer) when the original is loaded and not before the chat's history start.
- **Fragment quote** (any `Quote`): the title gets a small **quote icon** after it (`chat-quote-outline`); the description is the **quote parsed as markdown and rendered**, in multi-line mode: `white-space: pre-wrap`, wrapping at the block's width, **no CSS line clamp**. The line cap is done on the markdown tokens: **at most 7 source lines** (a constant `7`); each soft break and each blank line between blocks counts one; a code fence uses its fence lines; when the quote has more, the rest is dropped and **three ASCII dots** `...` are appended to the last visible text (or code), and open tags are closed. A fence cut in the middle gets `...` after its last kept line. Wrapped (visual) lines do not count: a very long single line is shown whole. The markdown is the messenger's markdown (block quotes only when the flag `enableBlockQuoteFormatting`, default off, is on); links are shown as text, no code interaction.
- **Plain reply** (no `Quote`, as the web client sends): single line (`white-space: nowrap`, `text-overflow: ellipsis`); the text is the original's preview (file name, «Голосовое сообщение», …), soft breaks and block ends turned into spaces, fences into inline code.
- **Click** on the block: scrolls to the original and **highlights the quote** in it for 600 ms (`ui.chunk.js @1287474`, matcher module `31683`, `app.js @1158266`): the quote's rendered text is searched in the original's rendered text, **case-insensitive, whitespace collapsed**, **every occurrence** is marked. Nothing in the wire says which occurrence was meant.
- **Composer bar** while a quote is pending (`ui.chunk.js @1430135`; style `.yamb-chat-bar__quote_text` = overflow hidden, ellipsis): title = the original's author, text = `selectionForQuote.plain` inside a quote-styled wrapper; cancel by the close button; clicking the bar jumps and highlights the fragment as above. No line clamp rule was found for the bar: it is one ellipsised line [INFERENCE from the style rule, not observed].
- The edit of a reply re-sends the same builder with the cached message's quote, so an edited reply keeps its `Quote` (as `research.md` says for the app).

## What could not be read from the bundle

The server side: (2) whether the string is validated against the original (substring, length, normalisation); (3) what newline and trim handling the server applies when it stores it (the client's own handling is above); (4) whether a quote above 200 characters is accepted (the web client sends it uncut as far as its code goes, so a live reader can see what the server returned for a web-sent long quote: 0.3); (5) how many real replies carry a fragment quote (0.3). The page config has no quote-related key. These stay with 0.3-0.6.

## Consequences for the design and specs (for 0.7 to decide; nothing here edits them)

1. **D9 wire.** Unknown (1) is closed: no extra key, so task 2.3 has **no work** for the request or for `wire.rs::relation`. The fragment is the `Quote` string. Open question for 0.6: the web client's plain reply sends `{}`; this app sends a 200-character `Quote`. A web reader very probably renders the latter as a fragment block. If 0.6 confirms it, the whole-message reply should omit `Quote` (this app already shows the original's preview when `quote` is absent), which makes the quote of `ReplyRef` optional and touches `write.rs`; that is a TS-Q decision, not a change made here.
2. **The quote text is markdown.** For the app's raw `Text.MessageText` the selected substring (trimmed, `\n`) equals what the web client would send for unformatted text; for a message with markup marks the web client's quote is the markdown of the **rendered** selection, which can differ from the raw substring. The app shows raw text, so it sends the raw substring: [INFERENCE] the web client shows both with the same markdown renderer, so a raw fragment renders the same.
3. **D10 timeline.** The web client shows up to **7** source lines with `...`, the spec says 3 with an ellipsis (`line_clamp(3)`); the composer bar shows one ellipsised line in the web client, the spec two. The task goal "so the timeline block matches" is the decision to take in 0.7: either keep 3 and 2 as deliberate app choices or move to 7 (the fragment block would then be taller than a bubble's text in the common case). The quote icon after the author is a cheap match.
4. **D9 `is_fragment`.** The web client does not decide "fragment or whole": any `Quote` is a fragment. The rule (quote differs from the first 200 characters of the original) is the app's own filter for old app replies and keeps whole-message replies one line. It stays correct for reading web fragments (a fragment equal to the whole short text shows as a whole-message quote, which looks the same).
5. **No offset on the wire.** A fragment is identified by its text only; the web client highlights all occurrences. The app's non-goal "jump to the original" stays a follow-up; when added, the same matcher rule (case-insensitive, whitespace-collapsed, all occurrences) is the compatible one.
6. **Menu/UX parity.** The web client has the popup on mouse up in addition to the menu entries; D6 (menu only) matches the help page's «правый клик → Цитировать». The web client refuses to send a quote with an empty own text; the `message-quotes` spec has no scenario for an empty own text, so task 2.x should decide and test it (the same refusal is the compatible choice) [decision for 0.7].
7. **Selection scope.** The web client allows a quote only from a selection inside one message of text kind; a multi-message selection offers none, as D6 says.
