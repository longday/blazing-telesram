# Research: replies and quotes in the real history (task 0.3)

Date 2026-11-28. Read-only scan of the app account's whole history; later sections (0.4, 0.6, 4.2) are appended here. Nothing was written to the account: `BT_WRITE_ONLY_CHAT` was set to a name that exists nowhere, and the only commands run were `bt-probe chats` and `bt-probe history <chat> [--before <micros>]`. **Names, guids, chat ids and message text stay in the VM and are not recorded here**: only counts, key names, value types, lengths and years/months.

## Method

- VM `bt-vm`, own tree `~/bt/src-TsR03` (`cargo build --locked --offline --release -p yandex-proto --bin bt-probe`), session `~/bt/.runtime`, `BT_LOG=yandex_proto::xiva=trace`. The raw `history` reply frames (`reply frame ... method=history body=<json>`) were parsed by a throwaway Python script that lived only in the VM. The script kept everything in memory; one short exploration run before it saved the raw output of a single chat in a `0700` scratch directory. The tree, the scratch directory and the script are deleted (checked). Per chat: the newest page, then `--before <oldest timestamp of the page>` until the footer says `reached_start=true` (page size 50), three chats in parallel.
- **Coverage:** 117 chats (44 Private, 71 Group, 2 Channel), **all 117 reached their start**, 643 pages, **28 489 rows**, 0 skipped, 0 failed, 223 rows with `Deleted` (they are inside the counts below, not excluded). (MP 0.1 saw 28 455 rows in the same 117 chats earlier the same day.) The scan ran three times: the first two (the second with more counters) agree on every number they share; the third (same chats, 28 489 rows, 55 Quote rows again) only compared the Quote rows whose original has no `Text` with `Gallery.Text` (added after review: the first two passes left those 5 rows uncompared).
- Row buckets: no `Plain` (system and other kinds) 2 266; `Plain` without `ForwardedMessageRefs`, `ForwardedMessageStyles` and `ForwardedMessages` 24 778; **reply** (those keys or `ForwardedMessages[]` present **and** own content: text, image, gallery, file, voice, sticker or poll) **1 369**; **forward without own content** 76.
- "Own" = `ServerMessageInfo.From.Guid` equals the session's guid. "CP" = `Plain.CustomPayload` is present.
- **The original's text** is `ForwardedMessages[0].Payload.Text.MessageText`; `ForwardedMessageRefs` was never needed (see below).

So **54 fragment quotes** of 55 (49 against `Text.MessageText` and 5 against `Gallery.Text`; 36 own, 18 other). The 49: 10 chats, 43 in Private chats and 6 in Group; by origin 27: 27, 28: 20, 200: 2; by month 2026-06 2, 07 12, 08 7, 09 10, 10 8, 11 10; 3 of the 49 replies were edited afterwards and still carry their `Quote`. The 5 caption fragments: 4 own (origin 27 three times, 28 once) and 1 other (27); the same `Plain` key set (`ChatId`, `CustomPayload`, `ForwardedMessageStyles`, `PayloadId`, `Text`), the same one-key style entry; every Gallery original has the same payload keys (`ChatId`, `CustomPayload`, `Gallery`, `PayloadId`; `Gallery` = `Items` (1 item each) and `Text`). **Every one of the 55 Quote rows is thus accounted for: 54 fragments, 1 whole, 0 non-substring.** (First pass of the scan counted the 5 Gallery rows as "original not text" and did not compare them; a second pass with the same chats and 28 489 rows compared them with the caption, see above.)

Shapes of the fragments (counted, no content; the statistics below that are marked "49" were taken over the text originals only, the five caption fragments are given separately):

- **Distinct shapes: one style entry shape** (`{Quote}`). Among the 44 middle/end fragments three `Plain` key sets, differing only by `CustomPayload` (absent on 2: origin 200) and `UrlPreviewDisabled` (2); the 5 from-the-start fragments all have `CustomPayload` and their other keys were not tallied. `ServerMessage` keys (from five sampled rows): `ClientMessage`, `ForwardedMessages`, `ServerMessageInfo`, `ReadsVersion` and (when set) the reaction keys; `ServerMessageInfo` keys: `From`, `SeqNo`, `Timestamp`, `Version`, `PrevTimestamp`, `LastEditTimestamp` (the 3 edited), `ThreadState` (seen on the origin-200 sample). The `ForwardedMessages` entry has `Payload` (`ChatId`, `PayloadId`, `Text`, `CustomPayload`) and `ServerMessageInfo` (and sometimes `Type`, item 6).
- **Length:** 4 to 208 characters (the five caption fragments are 10, 16, 17, 23 and 61 characters); of the 49: median 20, 38 are 40 characters or fewer (so 42 of 54); one is **208 characters (over 200), from the web client (origin 27, own, CP), stored and returned uncut**, original 784 characters with 9 newlines (the quote itself lies inside one line). Quote length against the original's: 1 % to 70 %, median 13 % (49). 14 are one word, 35 have two or more; 39 contain non-ASCII characters, **none an emoji or other astral character** (49); 10 start or end with a non-alphanumeric character; 3 contain `. ` / `! ` / `? ` (a sentence boundary) (49).
- **Newlines: none of the 55 quotes has a `\n`.** 21 of the 49 text originals do contain one (and 21 are over 200 characters, 3 over 1000); all 5 Gallery captions contain one (1 to 19 newlines; 73 to 1 748 characters); but every quote lies inside **one line** of its original: **no multi-line fragment exists in the history**, so unknown (3) for newlines has no observation here. **No leading or trailing whitespace in any of the 55**, consistent with the web client's `trim` (research-bundle.md); whether the server trims is not shown (the web client trims first).
- **Ambiguity:** each of the 49 text-original quotes occurs **exactly once** in its original (exact and case-insensitive). Of the 5 caption quotes, **one occurs twice** (exact match, 17 characters) in its caption, the other four once: the web client's "highlight every occurrence" had to choose nothing, and a repeated fragment does exist in the real data (the wire carries no offset).
- **Markdown:** the originals are **raw markdown strings** (11 of the 49 text originals contain a mark: `**`, `__`, `~~`, `++`, a backtick, `](` or a line-start `> `; marks in the five captions were not tallied). **3 of the 55 quotes contain a mark** (1 of the 49, 2 of the 5 caption quotes; same mark set as above); **2** of the 49 have a mark character just outside or just inside their edge (not tallied for the captions). All 54 fragments are exact substrings of the raw original (or raw caption), so the web converter's output (marks re-emitted around a selection, research-bundle.md) never differed from the raw substring in this data; but with only a handful of selections that touch or contain a mark this does not test the `**hello**` case (a selection inside a bold span whose marks lie outside it) and **proves nothing about it**: 0.4 must send one.
- The reply's own text is never the original's (0 of 49 text-original fragments quote one's own message with the same text).

Whole-message replies from the web client carry **no `Quote` at all** (1 314 rows; 1 146 of them have a text original, 160 of those longer than 200 characters and 220 with a newline). A reader therefore must show the original's `preview_text` for them, which the app already does (`yandex_backend.rs`).

## Consequences for 0.4, 0.6, 0.7 (decisions stay with them)

1. **0.4 must run.** Gate of tasks.md: fewer than three distinct fragment shapes (one style-entry shape; the `Plain` variants differ only by CP and `UrlPreviewDisabled`) **and** none with a newline (the one over 200 characters exists). Needed observations: a fragment with `\n` (also with a blank line), several over 200 characters (the web client sends them uncut; the 208 is one example), a selection **inside** a bold/italic/code span and one crossing a mark, a selection that occurs twice in the original (one such quote exists in a caption, but the wire cannot tell which occurrence), a plain web reply read both from `history` and from a raw `listen --watch` push (is `[{}]` visible anywhere), the `Type` value of a fragment row.
2. **0.6 stays needed** for unknown (2): every one of the 54 real fragment quotes is an exact substring, so the history cannot say whether the server validates; and for the app-sent forms (whole, trimmed, padded, 250 characters).
3. **For 0.7 / D9:** (a) `is_fragment` ("the quote differs from the first 200 characters of the original") classifies all 54 as fragments and the one app-sent whole reply as whole; no real row is the app's 200-cut, so the rule's old-reply branch is not exercised by the real data. For a Gallery original the "original text" the rule compares with is the **caption** (`Gallery.Text`): 5 of the 54 fragments, so the adapter's text of a gallery original (2.4) must be its caption, not `preview_text`. (b) A fragment that begins at the first character of a short original is a prefix, not a whole quote, **5 of 54**: the rule handles them (quote shorter than `original[..200]`). (c) The wire has **no key for a fragment but `Quote`**, confirmed on 55 rows; nothing else needs a decoder in `wire.rs` (2.3 has no work from this scan). (d) The app's writer sends `[{Quote}]` for every reply while the web client's plain reply leaves **no trace** in the history: whether an app whole-message reply should stop sending `Quote` is still 0.6's question (the web reader shows any `Quote` as a fragment block, research-bundle.md); in the real history the one app-sent row is shown by the app as a whole.
4. **Reading side:** `ForwardedMessageRefs` never arrives in history rows (item 1), so `Relation::Reply.reference` is `None` there and everything keyed on it (the quote's link to the original) must use `original.timestamp`; check that the fragment code does not need the reference.
