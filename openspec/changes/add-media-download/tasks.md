# Tasks

Each task is session-sized and names the files it owns; tasks that share no files and no dependency run in parallel. Contract names (`Command::Download`, `ClientEvent::Download*`, `DownloadFailure`, `GalleryItem`, `Backend::download`, `ProtoError::Storage`, …) are fixed in `design.md` Decision 3, so dependent tasks can start from the design text; "depends on" marks where compiling or testing needs the other task's code.

Waves: **A** (parallel): 1.1, 2.1, 2.2, 5.1 · **B** (parallel, after A): 1.2, 2.3, 3.1, 4.1 · **C** (parallel, after B): 4.3, 1.3 · **D**: 4.2 (needs `open_viewer` from 4.3) · **E**: 5.2.
`main.rs`, `tests.rs`, `model.rs`, `client.rs` and `yandex_backend.rs` are touched by more than one task, always in different hunks (noted per task); read the current file before editing and keep diffs additive.

**Merge units and file ownership (see `openspec/changes/DEPENDENCIES.md`).** A task starts only when no in-flight task of any change edits one of its files; every merge to `main` compiles with no stubs. Because of that: **1.1** also owns one hunk of `crates/desktop/src/yandex_backend.rs`, the new `ProtoError::Storage` arm of `backend_error` (mapped to `BackendError::Protocol` with a storage message; 3.1 later maps it to `BackendError::Storage`), and merges alone; **2.2** merges alone (it also owns the `mod paths` line in `crates/chat-core/src/lib.rs`); **2.1, 2.3, 3.1, 4.1 are one unit** (2.1 adds required `Backend::download`, `Command`/`ClientEvent` variants and `BackendError::Storage`, which need the engine arms of 2.3, the backend of 3.1 and the store arms of 4.1 to compile) on the branch `integ/md`, merged to `main` together; **4.3**, then **4.2** merge one by one; **5.1** (README) merges together with the last unit, after the feature exists.

## 1. Protocol crate (`crates/yandex-proto`)

- [x] 1.1 Streaming original download. Owns `src/media.rs`, `src/net.rs`, `src/client.rs`, `src/error.rs`. Add `MediaTarget::Original { file_id }` with URL `{files_base}/file_shortterm/{safe_path(file_id)}?attach=true`; `net::http_client_streaming` (connect timeout + `read_timeout(request_timeout)`, no total timeout); `MediaClient::download(target, out, progress)` per design Decision 2 (same cookie rule and status mapping as `fetch`, no 25 MiB cap on this path, short body when `Content-Length` is known → `ProtoError::Network`, write failure → new `ProtoError::Storage`); `Client::download_media` facade. Tests in `media.rs` (stub server from `registry::stub`): URL template and hostile ids for `Original`; bytes and progress/total reported; body above 25 MiB is accepted; 401/404/403/5xx mapping; truncated body fails; stalled server fails after the idle timeout while a slow but steady body succeeds; a redirect to a second local server (other port) arrives without the `Cookie` header; log record has host/path/status/elapsed and no query, cookie or body (extend the existing `log_shows_the_request_without_its_query` pattern); a failing writer yields `Storage`.
- [x] 1.2 `bt-probe download`. Owns `src/bin/bt-probe.rs`. `bt-probe download <chat> <micros> [--item N] [--to <dir>]`: loads the history page, takes the file or the `N`-th image of the message with that timestamp, downloads it into `--to` (default the current directory, refusing to overwrite) through `Client::download_media`, prints final byte count, announced size, status and the target host and path (never the query, never cookies), exits non-zero with the error class on failure. Update the `USAGE` text and the module doc. Unit-test the argument parsing like the other commands. Depends on 1.1. Implementation notes: `--item` is 1-based (default 1; a single file or image accepts only 1); the file is created with `create_new` directly under the sanitized server name (last path component, no control characters or colons, id segment as fallback) and removed again when the transfer fails; output lines are `received`, `announced size (FileInfo.Size)`, `content-length` (from the last progress call), `size check` (matches / DIFFERS / unknown), `status: 2xx` (`download_media` returns only on 2xx; the redirect target is in the `BT_LOG=yandex_proto=debug` record, field `landed`) and `target` (host and path of the request); failures print `download failed (<class>): …` with class `session-expired`, `network`, `protocol`, `not-found`, `storage` or `commit` and exit 1.
- [x] 1.3 Live re-check with the Rust client. Owns the "Live verification" section of `design.md` (the only edit). The URL template was already verified live with plain GETs (`design.md` "Live verification": `disk/<uuid>` images, two redirect hops, size equals `FileInfo.Size`); this task repeats it with the real code path. Using the stored session (`BT_RUNTIME_DIR=<repo>/.runtime`), run `bt-probe download` on (a) a non-image file above 25 MiB (the group chat that holds the files lists them with `bt-probe history`; the self chat holds none) into a temporary directory, and (b) one image; record that the byte count equals `FileInfo.Size`, that progress totals match `Content-Length`, that nothing above the 25 MiB cap was refused, and delete the downloaded files afterwards. If a result contradicts Decision 2, fix `MediaTarget::url` in `media.rs` and update Decision 2 in the same commit before 3.1 and 5.2 are accepted. Depends on 1.2. A missing or expired session is recorded as an observed blocker, not as a pass.
