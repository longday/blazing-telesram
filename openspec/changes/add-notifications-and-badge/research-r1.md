# Research R1: notification centre and Dock badge, identity

Run 2026-11-28 in the Tart VM `bt-vm` (macOS 26.6.2, build 25G83, Rust toolchain 1.100.0), in a scratch crate outside the repository (`~/bt/src-NbR1/scratch`, deleted), no account, no write of any kind. Linked against `objc2 =0.6.5`, `objc2-foundation =0.3.2`, `block2 =0.6.2`, `objc2-app-kit =0.3.2`, `objc2-user-notifications =0.3.2` with `default-features = false`; `Cargo.lock` of the repository was the base and the only new package was `objc2-user-notifications 0.3.2` ("Locking 1 package"). The scratch program (an `NSApplication.run()` with a main-thread timer that executed commands from a file) drove every call below; banners, prompts and the Dock were observed by screenshot and, for the Dock label, by the accessibility attribute `AXStatusLabel` of the Dock item (`System Events`, process `Dock`). Screenshots were deleted after the booleans were written down; the VM's directories were removed and `ls` confirmed.

## Result in one block

- **D3 outcome: 2.** The bare `cargo run` binary cannot use `UNUserNotificationCenter` (the process aborts); a minimal **ad-hoc-signed** `.app` (four `Info.plist` keys, `codesign -s - --force`) can: prompt, banner, click with the chat id, withdraw. An unsigned `.app` (the binary as cargo links it, only copied) cannot. N-B (question 7) was not run: outcome 2 holds.
- **The Dock label depends on the notification permission once the process has a bundle identity that the system knows**: shown only when the authorization is granted **and includes `Badge`**; hidden when undetermined (it appears the moment the permission is granted, without a new `set`), denied, or granted without `Badge`. A process the notification system does not know (the bare binary, an unsigned bundle) shows the label with no permission at all. So the notifier requests alert, sound **and badge**, and `design.md` D2 ("No authorization needed") and D9 ("the badge still works" after a refusal) change (task 0.4).
- Exact cargo feature lists are at the end.

### Prompt

The permission prompt is **a notification banner**, not a dialog: top right, `"<CFBundleName>" Notifications — Notifications may include alerts, sounds, and icon badges.`; an `Options ▾` button appears on hover, and its menu has `Allow` and `Don't Allow`. In the VM (1440×900 points) it was answered with the helpers of `docs/vm.md` section 4: `move.js 1250 82`, `click.js 1373 98` (Options), `click.js 1365 131` (Allow) or `click.js 1380 155` (Don't Allow). `requestAuthorization`'s completion arrives only after the answer (tens of seconds later) on a non-main thread; `granted` is true for Allow; after Don't Allow `authorizationStatus` reads 1 (the completion's `granted` was not logged). The VM does show banners, so the "use `getDeliveredNotifications` as the observation" fallback was not needed.

## What this means for the code tasks

- **5.1 `notifier::create()`**: `NSBundle.mainBundle.bundleIdentifier()` nil → `None` with one `info` line, before any `UNUserNotificationCenter` call (the call kills the process). A non-nil identifier is **not** proof that notifications work (unsigned bundle, embedded plist): there `requestAuthorization` completes with `granted=false` and error code 1, `getNotificationSettings` stays at 0 (`not determined`) and `addNotificationRequest` fails with code 1. The notifier maps a completion with `granted=false` (error or not) to `Denied`, and `permission()` reads only `authorizationStatus` (0 undetermined, 1 denied, 2 authorized, 3 provisional, 4 ephemeral; the per-feature settings read 2 even after a refusal and must not be used). `show` while not `Granted` does nothing. A delegate object is created before the first request, set with `setDelegate`, and **owned by the notifier**; `willPresent` answers `Banner|Sound`; `didReceive` reads `userInfo["chat"]` and sends it on an `async_channel`; the `define_class!` needs no thread kind (works as `AnyThread`).
- **5.2 the bundle wrapper**: four plist keys are enough; the bundle **must be ad-hoc signed after every copy** (`codesign -s - --force <App>.app`; the cargo-linked binary is `linker-signed` and fails); the executable is run **directly** (`Name.app/Contents/MacOS/<exe>`), which is what was tested (`open`/Finder launch was not); the permission survives a rebuild and re-sign of the same identifier. The bundle identifier is the key of the stored answer: the wrapper's identifier is fixed once (a change asks again).
- **D2/D9 (task 0.4)**: request `alert`, `sound` and `badge` together; the label needs the authorization with `Badge` when the process has an identity; under `cargo run` (no identity) and in an unsigned bundle it needs nothing; a refusal also hides the label of a signed bundle. A label set before the answer is not lost.

## Exact cargo feature lists

Verified by compiling in the VM (`cargo check --offline`, zero warnings) a crate that uses exactly what tasks 3.1 and 5.1 need (`NSApplication::sharedApplication(mtm).dockTile().setBadgeLabel(..)`; `NSBundle.mainBundle.bundleIdentifier()`; the `define_class!` delegate with both methods; `setDelegate`, `requestAuthorizationWithOptions:completionHandler:`, `getNotificationSettingsWithCompletionHandler:`, `UNMutableNotificationContent` with title, body, thread identifier, sound, user info; `UNNotificationRequest::requestWithIdentifier_content_trigger(.., None)`; `addNotificationRequest:withCompletionHandler:`; `getDeliveredNotificationsWithCompletionHandler:`; `removeDeliveredNotificationsWithIdentifiers:`; `removeAllDeliveredNotifications`), with `objc2 =0.6.5` and `block2 =0.6.2` as in `crates/desktop/Cargo.toml`, then removing each feature in turn:

```toml
objc2-user-notifications = { version = "=0.3.2", default-features = false, features = ["std", "block2", "UNNotification", "UNNotificationContent", "UNNotificationRequest", "UNNotificationResponse", "UNNotificationSettings", "UNNotificationSound", "UNNotificationTrigger", "UNUserNotificationCenter"] }
objc2-app-kit = { version = "=0.3.2", default-features = false, features = ["std", "NSApplication", "NSDockTile", "NSResponder", "NSScreen", "NSWindow", "objc2-core-foundation"] }
objc2-foundation = { version = "=0.3.2", default-features = false, features = ["std", "NSString", "NSURL", "NSBundle", "NSArray", "NSDictionary", "NSError"] }
```

- `objc2-user-notifications`: every `UN*` module above and `block2` is **required** (removing any one is a compile error; `UNNotificationTrigger` only because `requestWithIdentifier_content_trigger` is gated on it, although `None` is passed). `bitflags` is implied by `UNUserNotificationCenter` and is not listed; `std` compiles either way and is kept for the repository's convention. The default feature `objc2-core-location` is **not** enabled (it would add a package that is not otherwise in the tree).
- `objc2-app-kit`: the two **new** features are `NSApplication` and `NSDockTile`; both are required, and `NSResponder` (already there) is required by them. `NSScreen`, `NSWindow`, `objc2-core-foundation` stay for the existing screen code.
- `objc2-foundation`: the only **new required** feature is `NSBundle`; `NSArray`, `NSDictionary`, `NSError` are implied by the `UN*` features but used directly by the notifier, so they are listed. Avoid `NSArray::iter` (it needs `NSEnumerator`): `to_vec()` needs nothing more.
- `Cargo.lock`: one new package, `objc2-user-notifications 0.3.2`, with its edges to `bitflags 2.13.2`, `block2 0.6.2`, `objc2 0.6.5`, `objc2-foundation 0.3.2` (all already locked), plus the dependency edge in `blazing-telesram`.
