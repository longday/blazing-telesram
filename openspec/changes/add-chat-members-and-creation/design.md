# Design

## Context

See `proposal.md` for motivation and the resolved decisions; `research.md` for sources. What the code looks like today:

- Reads are a closed enum, `ReadRequest` in `crates/yandex-proto/src/request.rs`, with `ALLOWED_METHODS` listing exactly eight names on `main` today: `request_user`, `get_users_data`, `history`, `subscribe`, `search` (`add-global-search`), and `whoami`, `get_chat_members`, `get_group_members` (task 1.1 of this change; the first four were the whole list before it). Task 1.2 found `get_group_members` unusable (see "Observed shapes"), so task 1.3 removes it and the list becomes seven names. Tests pin the list (`request.rs`: `allowlist_has_no_mutating_or_presence_methods` forbids names containing `create_`, `leave`, `invite`, `set_` and the other markers, asserts the exact list and its length; `write.rs`: `the_read_allowlist_does_not_gain_the_write_method` asserts the exact list).
- Writes are the closed `WriteRequest` (`write.rs`): socket method `push` only, `ClientMessage` variants `Plain`, `SeenMarker`, `Typing`. There is no Registry (HTTP) mutation anywhere: `RegistryClient::execute` (`registry.rs`) takes only `&ReadRequest`, fetches a CSRF token when the route says so, maps `status != "ok"` to `ProtoError`, logs method and status at debug and the reply body only at trace.
- `whoami` is not sent by the client. `frame.rs` can encode it (`encode_whoami_is_byte_exact`), `request_user` (HTTP) is used by `bootstrap` for identity (`guid`, `uid`, `display_name`). The reference documents `whoami: { Guid } -> { UserInfo, UserStatusInfo, CurrentTime }` with `UserInfo { Guid, Uid, DisplayName, PublicName, Nickname, AvatarId, ... }` and `UserStatusInfo { UserStatus: {}, Timestamp }`.
- The reference catalogue (`docs/protocol-research.md` §7, §10): `get_chat_members` → `{users, groups, departments}` with `users[].role`; `get_group_members` is listed the same way but is unusable (`bad_request` for every shape, task 1.2); `create_private_chat { guid, wait_for_update, onetime_user_token }`; `create_chat { alias, ... }` opaque. Mutations are CSRF-guarded (`X-CSRF-TOKEN`); the member reads carry no CSRF flag, and task 1.2 confirmed live that none is needed.
- `chat-core::Backend` (`backend.rs`) has `bootstrap`, `chat_list`, `history`, `fetch_media`, `subscribe`, `watch`, `send_text`, `edit`, `delete`, `mark_seen`, `typing`; `BackendError` has `Rejected { reason, permanent }`. `YandexBackend` (`crates/desktop/src/yandex_backend.rs`) maps `ProtoError` to it, holds `Connection { client, events, me }` (`me` = own guid) and applies the `BT_WRITE_ONLY_CHAT` guard to every `push`. Private chat ids look like `<guid>_<guid>`; `WireChat.partner_guid` already exists but `ChatSummary` drops it.
- The engine (`crates/chat-core/src/client.rs`) is one `Engine<B>` with `Command`/`Input`/`Action` enums, a cache and an event channel; the desktop `ChatStore` (`store.rs`) turns `ClientEvent` into `StoreEvent`; `Desktop` (`desktop.rs`) owns overlays (`AccountMenu`, `delete_pending`, `LogView`) that make `blocked()` true.
- Mockups: `docs/mockups/3-info.svg` (chat info), `docs/mockups/6-settings.svg` (settings/profile). Only the read-only subset is built.

## Goals / Non-Goals

**Goals:** the three capabilities in `specs/`; mutations limited to a closed, tested pair of Registry methods; no creation without confirmation, no automatic retry of creation.

**Non-Goals:** any management beyond creation (see proposal Non-goals); caching members; directory search; avatars upload; showing presence; showing the `groups` and `departments` entries of a member list.

## Decisions

### D1. Two new reads in the closed read set
`ReadRequest` gains `Whoami { guid }` (socket, body `{Guid, RequestId}`; route `Socket`) and `ChatMembers { chat, limit, guid_offset, roles }` (`get_chat_members`, `Route::Registry { csrf: false }`, params `{ "chat_id", "limit", "guid_offset"?, "roles"? }` as the web client sends them). `ALLOWED_METHODS` ends as the exact seven names `request_user, get_users_data, history, subscribe, search, whoami, get_chat_members` (the four existing ones, `search` from add-global-search, and the two reads here); the existing tests are updated to that list and still reject any mutating-looking name. Task 1.1 landed a first form (`ChatMembers { chat }` plus `GroupMembers { chat }`, eight names); task 1.3 brings it to this form.
Which chats can be listed was settled by the live probe of task 1.2 (details under "Observed shapes"). `get_group_members` is not part of the set: it answers `bad_request` for every chat and parameter shape tried and the web client never calls it. `get_chat_members` works for **groups** only: 20 users per page by default, `limit`, `guid_offset` and `roles` page and filter it, the reply has no total and no "more" flag (a page shorter than `limit` is the last one). It answers HTTP 403 `no_permissions_for_this_chat_operation` for private chats, the self chat and (for this account) channels. So the backend asks `get_chat_members` for `ChatKind::Group` and `ChatKind::Channel` (for a channel a refusal is shown as "list not available to this account", never as an empty list) and never for `ChatKind::Private` (self chat included): a private chat is answered without a request from the chat row, which carries the partner.
`Client` keeps the guid of the session (`session.identity.guid`) to fill `Whoami`. Typed accessors `Client::members(chat, limit, guid_offset)` (no chat-kind argument: the backend decides which chats to ask) and `Client::whoami()` return parsed wire models (`WireMembers`, `WireProfile`); the raw-JSON accessors of task 1.1 stay only until task 1.3 replaces them.
Alternative: read the profile from `request_user`, which bootstrap already calls. Rejected for the profile view: it returns identity fields only, while `whoami` carries `UserStatusInfo`; `request_user` stays the identity source for bootstrap.
The member reads need no CSRF token (task 1.2 never saw `bad_csrf_token`), so the route stays `csrf: false`.

### D2. Closed Registry mutation set in a new module
New `crates/yandex-proto/src/manage.rs` with `ManageRequest` (initially only `CreatePrivateChat { guid }`; `CreateChat` is added by task 6.1 if the gate passes), `MANAGE_METHODS` (`["create_private_chat"]`, plus `create_chat` later) and `registry_body()`. `RegistryClient::manage(&ManageRequest)` always fetches a CSRF token first and shares the header/cookie code with `execute`, but is a separate entry point: `execute` keeps accepting reads only, so a mutation cannot be built through the read path and no generic "call any method" exists. Tests assert: the method list is exactly `MANAGE_METHODS`; none of its names is in `ALLOWED_METHODS`; no name of the deferred management set (`change_chat_members`, `change_chat_role`, `change_chat_admins`, `leave`, `invite`, `invite_renew`, `set_chat_info`, `create_token`) is representable; the CSRF header is sent; cookie and token values never reach the log (the existing `registry` log test is the model).
`create_private_chat` params: `{ "guid": <guid>, "wait_for_update": true }`; `onetime_user_token` is omitted (the token comes from `create_token`, a different mutating method, which this change does not add). If the live check (task 5.1) shows the server refuses without it, private creation moves to a follow-up exactly like group creation (D4 fallback).
Alternative: put creation on the socket `push` path. Rejected: the reference lists creation as Registry methods; `push` carries messages only.

### D3. Outcome classification: not sent, rejected, unknown
A repeated creation can duplicate a chat, so the transport layer reports what it knows: `manage` returns `Result<Json, ManageError>` where `ManageError` is `NotSent(ProtoError)` (CSRF exchange failed, or the connection could not be opened: nothing left the client), `Rejected(ProtoError)` (HTTP 401 = session expired, or a reply whose `status` is not `ok` with its `data.code`: the server answered and did not create) or `Unknown(ProtoError)` (the request was sent and the reply is a timeout, a dropped connection, HTTP 5xx/429 or a non-JSON body). A reply with `status: "ok"` is success even if the chat id cannot be found in it. `Backend::create_*` returns `Result<Option<ChatId>, CreateError>`, `CreateError = Failed(BackendError) | Unknown(String)`; `NotSent` and `Rejected` map to `Failed` (SessionExpired stays `SessionExpired`), `Unknown` carries a reason string without cookie or token values.
Alternative: reuse `BackendError::Network` for everything. Rejected: it cannot say whether the chat may exist, and the spec requires that distinction.

### D4. Gate for group creation (`create_chat`)
`create_chat` has opaque parameters in the reference, so it is not implemented blindly.
1. Task 0.1 (read-only, no account effects, can start immediately): read the web client's JavaScript bundle (the reference's `docs/protocol-research.md` cites it as the source of its §7 parameter shapes) and record the `createChat` parameters (title field name, participant list field and element form, optional fields, default values) and the reply shape under "D4 outcome" below.
2. If the payload is fully determined (static PASS): task 6.1 adds `ManageRequest::CreateChat`, its tests and `bt-probe create-chat --confirm-create` with the recorded shape and nothing else; task 6.2 runs that probe once with the user's approved throwaway title and participants and checks the group in the web client, which fixes the payload and the reply shape (live PASS). Only then do 6.3 (backend, engine, store) and 6.4 (UI) start.
3. Fallback: if step 1 cannot determine the payload, or task 6.2 fails for a reason the client cannot correct (the server refuses the recorded shape), task 6.F deletes group creation from `specs/chat-creation/spec.md` (the requirement "Group chat" and the group wording in "Explicit confirmation"), removes any group code already written, and adds the follow-up `add-group-chat-creation` to `proposal.md`. Everything else in the change is unaffected and still archivable.

**D4 outcome:** recorded here by task 0.1 (static result: payload and reply shape, or "not determined") and by task 6.2 (live result). Gates: 6.1 needs a static PASS; 6.3 and 6.4 need a live PASS. Until the static result is recorded no group task starts.

**Static result (task 0.1, 2026-11-24): PASS.** The payload is fully determined by the web client's own code, in two independent bundle versions. No request was sent to the account: only public, cookie-less GETs of static files on `yastatic.net` and of the public `https://yandex.ru/chat/` page. No participant, title or account data was involved.

Sources (both minified webpack bundles, read as text):
- `https://yastatic.net/s3/chat-static/_/0x8b21684/web/app.js` + `ui.chunk.js` (the build the reference cites as `chats-web/3.21.0`): `createChat(e){return this.request("create_chat",e).then(R)}` in the registry API class of `app.js`; the only group/channel caller is the action `Xe` (exported `P4`, module 77964 of `app.js`) used by the create-chat wizard `CreateChatWizardContainer` in `ui.chunk.js`.
- `https://yastatic.net/s3/chat-static/telemessenger/_/3.6.3/web/app.js` + `ui.chunk.js` (what `https://yandex.ru/chat/` serves today): same `createChat(e){return this.request("create_chat",e).then(x.o)}`, caller `e3` (`app.js`) and wizard step `ef.onCreate` (`ui.chunk.js`). The wizard is the same for "Create group" (`channel:false`) and "Create channel" (`channel:true`).

**Envelope.** Registry POST, multipart field `request` = `{"method":"create_chat","params":<payload>}`, no per-call options, so the transport default applies: `X-CSRF-TOKEN` header (CSRF on), retried by the web client only on `bad_csrf_token`. Success is `status: "ok"` with the result in `data`.

**Payload** (`params`), fields in the order the client builds them:

| field | type | rule from the client |
|---|---|---|
| `name` | string | the group title as typed; the wizard disables "next" while `name.trim()` is empty, so the client never sends a blank title; the length limit `maxChatTitle` is 250 (server config injected in the page) |
| `description` | string | always sent, `""` when the user typed nothing; limit `maxChatDescription` 500 |
| `permissions.users` | array of string | the participants' **guids** (`member.data.guid`), plain strings, not objects; the code does not add the caller's own guid (the wizard's contact list excludes the signed-in user), so 6.1 must not list it either |
| `permissions.groups`, `permissions.departments` | array | **only in the older/flag-off form**: `group_id` / `department_id` values, `[]` when none are picked |
| `group_refs`, `department_refs` | array of `{id, organization_id}` | **only in the flag-on form** (the form of 3.6.3, chosen by the feature flag `enableImprovementsFederations`, default false in code, `true` in the flags the public page serves today): replaces `permissions.groups`/`departments`, `[]` when none are picked; `permissions` then holds `users` only |
| `channel` | bool | `false` for a group chat, `true` for a channel |
| `is_public` | bool | the wizard's form object starts with `isPublic: true` and the group wizard has no control to change it, so the client always sends `true`; in chat info the same property is edited as `public` for groups and `is_public` for channels (`public` is derived from `invite_hash` on read), so what `is_public: true` does to a group (link-joinable or not) is not shown by the code |
| `avatar_id`, `key` | string | optional: merged in only after the client uploaded an avatar (`upload_avatar`); never sent otherwise; this change omits them |

No other fields exist in either build: in particular no `alias` (the reference's `{ alias, ... }` is the optional vanity name; the wizard does not send it and `check_alias` is a separate method), no `version`, no `wait_for_update`, no one-time token.

**Example body, flag-on form (current production client, one participant, no groups/departments):**

```json
{"method":"create_chat","params":{"name":"Test group","description":"","permissions":{"users":["<guid>"]},"group_refs":[],"department_refs":[],"channel":false,"is_public":true}}
```

Flag-off form (the older bundle): `{"name":"Test group","description":"","permissions":{"users":["<guid>"],"groups":[],"departments":[]},"channel":false,"is_public":true}`.

**Reply shape.** `data` is `{ "chat": { "chat_id": "<id>", ... }, "errors": [ { "code": "<code>", ... } ] }`; the client's normaliser keeps `errors` and runs `normalizeYambGroupChat` over `chat`. The only field the client relies on is `chat.chat_id` (group ids look like `0/0/<guid>`); the rest of `chat` is the usual chat-info object (`name`, `description`, `members`, `version`, `invite_hash`, `rights`/`role`, ...). `errors` is optional and non-fatal: when present and non-empty the chat **exists** and the toast lists participants that could not be added (codes seen in the bundle: `blocked_by_privacy_settings`, `join_denied`, `no_guest_access`, `federation_no_mutual_friendship`). A rejected call is a registry error (`status` not ok, `data.code`), and the web client shows `error.create_chat`. After success the client opens the chat and loads its history with up to 3 retries 300 ms apart ("history not found" is logged, not shown), i.e. the new chat can be briefly invisible to reads: a list refresh straight after the reply may not yet contain it (D5 already opens it once it is in `chats`).

**What this fixes for the later tasks.**
- 6.1: `ManageRequest::CreateChat { title, users }` builds the flag-on form above with `description: ""`, `channel: false`, `is_public: true` (the values the web wizard sends), empty `group_refs`/`department_refs`; the tolerant reply parser takes `data.chat.chat_id` (`Option`) and keeps `errors` only as a count and the codes for the log; a `status: ok` reply without an id is still success (D3). The probe's confirmation text must print the title, every guid and the `is_public: true` value.
- 6.2 must settle live, because the code cannot: (a) which of the two forms the account's server accepts (the flag value of the signed-in account is not readable without an account request; if the flag-on form is refused with a validation error, try the flag-off form once and record the result); (b) what `is_public: true` means for a group, and whether the user accepts a throwaway group created that way (if the server also accepts `false`, prefer it and record it); (c) the real reply shape and whether the new chat shows up in a list refresh at once.
- Residual risk that stays with 6.2 and the 6.F fallback: none of the above was observed against the server; the code says what the web client sends, not what the server tolerates.

**Incidental static finding for task 5.1 (private chat, does not replace its live check).** In both bundles `createPrivateChat(guid, waitForUpdate, token)` sends `{ guid, wait_for_update, onetime_user_token }` with `undefined` values dropped by `JSON.stringify`. The callers pass `waitForUpdate` as `undefined` unless their own optional argument says otherwise, and the token comes from `chatsMeta.chatIdToOneTimeToken[chatId]`, which only a one-time-token deep link fills. So the ordinary web flow sends `{ "guid": "<guid>" }` alone; D2's `{ guid, wait_for_update: true }` is a variant the web client can send but does not by default, and `onetime_user_token` is not required by the client's own default path. The web client also does not call `create_private_chat` when a person is opened from search unless the person is a robot: it builds a local transient chat there and calls `activate_chat` from its "ensure chat" path ([INFERENCE]: that is, when the first message is sent); the reply is `{ chat, user }`.

### D5. Creation flow in the engine: no queue, no retry
New commands `CreatePrivateChat { user }` (and `CreateGroupChat { title, users }` from task 6.3); events `ChatCreated { chat: Option<ChatId>, existing: bool }` and `CreationFailed { reason: String, unknown: bool }`. The engine handles a creation like an `Action` (attempted once, not queued, nothing persisted):
- one creation at a time; a second command while one is in flight is ignored (the UI also disables the button);
- offline (`!is_online()`): `CreationFailed { unknown: false }` without a request;
- private chat that already exists in the cached list (`ChatSummary.partner == user`): `ChatCreated { chat: Some(id), existing: true }`, no request;
- success: refresh the chat list (the path `become_online` uses), then emit `ChatCreated` with the id from the reply, else, for a private chat, the list entry whose `partner` is the user, else `None`; the store opens it once it is in `chats`;
- `Failed`: `CreationFailed { unknown: false }`; `Unknown`: the same list refresh, then, if the refreshed list holds a private chat whose `partner` is the user, `ChatCreated { chat: Some(id), existing: true }` (the chat appeared after all: the client cannot tell its own request created it), else `CreationFailed { unknown: true }`. Nothing re-sends by itself; the next attempt is the user pressing "Создать" again, and for a private chat the check above opens a chat that appeared in the meantime.
`ChatSummary` gains `partner: Option<UserId>` (`#[serde(default)]`, so cached rows from before still load) filled from `WireChat.partner_guid` in `summary()` of `yandex_backend.rs`; the struct-literal sites (`chat-core/src/fixtures.rs`, `desktop/src/tests.rs`, `yandex_backend.rs`) follow; the `unread_chat` helper in `client.rs` tests uses struct update and needs no change.

**Review fix: the refresh outcome is part of the answer.** `handle_chats` ignores a failed list read, so the engine records whether the read that follows a creation succeeded (`listed`). `Unknown` with a successful read that does not hold the chat stays `CreationFailed { unknown: true }` (the dialog may say the list was refreshed). `Unknown` with a failed read is the new `ClientEvent::CreationUnverified { reason }` (store: `CreationState::Unverified`, dialog notice `new-chat-unverified`): the chat may exist unseen and the dialog says the list could not be read. The engine then sets `creation_unverified`, and the next `CreatePrivateChat` (any person; the unseen chat may be anyone's) first reads the list (`Input::ListChecked`): a failed read emits `CreationUnverified` again with no request sent, a read that holds the private chat with that person emits `ChatCreated { existing: true }`, any other successful read clears the flag and sends the request. `switch_account` clears the flag. The decision "retry stays the user's press" is unchanged; only the check in front of it is mandatory.

**Review fix: `chat: None` is opened later.** `ChatStore` remembers the person of the creation in flight (`creating`); when `ChatCreated { chat: None }` ends it, the pending selection is "the private chat with that person" (`PendingOpen::Partner`) instead of a chat id, and `open_pending` selects it once any `ChatsReplaced`/`ChatUpdated` holds a private chat whose `partner` is that person. Any selection by the user, a new creation, `SessionExpired` and `SignedOut` drop it. This implements the spec text ("opened once it appears in the chat list") instead of amending it; the earlier decision "`chat: None` selects nothing" is withdrawn.

### D6. Members and profile in the engine and store
Domain types in `model.rs`: `MemberRole { Member, Admin }` (`role` `"admin"` is `Admin`, every other value or none is `Member`; the order of the list is not relied on), `Member { user: UserId, name: Option<String>, avatar: Option<MediaRef>, role: MemberRole, me: bool }` (`me` set by the backend, which knows the own guid), `ChatMembers { chat, users, partial: bool }` (`partial` is true when the page bound was reached and more members may exist: the server sends no total, so the panel can say only how many are shown), `Profile { user, name, avatar, status_text }`. Commands `LoadMembers(ChatId)` (kind looked up in the cached summary) and `LoadProfile`; events `Members(ChatMembers)`, `MembersFailed { chat, reason, offline }`, `Profile(Profile)`, `ProfileFailed { reason, offline }`. Both are plain reads: offline answers at once with the `offline` flag, nothing is cached or persisted, duplicates of an in-flight load for the same chat are dropped. Names and avatars come from the member reply itself (`display_name` is always present, `avatar_id` usually); the existing `Users` helper (`get_users_data`, batched) fills only a row whose name is missing. Avatars become `MediaRef { Avatar }` and are fetched through the existing media path. The reply's `groups` and `departments` arrays were empty in every group of the account and their element shape is unobserved: no key is assumed, the parser accepts and ignores any array there, and no group or department type exists. Showing them waits for a recorded non-empty example (proposal Follow-ups). A private chat is answered from the cached chat row without a Registry request (task 3.1 places this in the backend): one user row for `ChatSummary.partner` with the name and avatar the row carries, role `Member`, and no row when the row has no partner. A permission refusal (HTTP 403 `no_permissions_for_this_chat_operation`) maps to a `MembersFailed` whose reason says the list is not available to the account.
`ChatStore` keeps `members: HashMap<ChatId, MembersState>` (`Loading | Ready | Failed`), the profile state and the creation state, and emits `StoreEvent::{Members(ChatId), Profile, Creation, ChatCreated}`.
`partial` rule: the server sends no paging marker and no total. The backend asks pages of 50 (`limit: 50`, then `guid_offset` = guid of the last user of the previous page) until a page holds fewer than 50 users, up to a bound of 20 requests (1000 members); `partial` is true when the bound is reached with a full last page. A failing later page fails the whole load; a shortened list is never delivered as complete.
`status_text` is `UserStatusInfo.UserStatus.CustomStatus.Text` when that is a non-blank string (path verified statically in the web bundle, see "Observed shapes"). `UserStatus` is `{}` when the account has no status (the only live observation, task 1.2) and a populated one was never seen, so `{}`, a missing `CustomStatus` or any other shape yields no status text; no availability is inferred.

### D7. UI placement
Three new modules in `crates/desktop/src/`: `info_panel.rs` (right-hand panel from the chat header: user rows, admin marker, "Написать" on rows other than `me`, loading/error/offline/partial/"not available to this account" states; a private chat shows its single partner row), `profile.rs` (read-only profile opened from the account menu next to sign-out; shares the `blocked()` treatment of overlays; offline and error states), `new_chat.rs` (dialog: person picker or title field, selected participants, "Создать"/"Отмена"; candidates = distinct `ChatSummary.partner` guids with the chat title as name, plus the members loaded for the open group, minus `me`). "Новый чат" is a button beside the search field in `Desktop::sidebar`, disabled unless `ConnectionState::Online`. Escape closes each overlay; Enter in the dialog's fields never triggers creation, only the "Создать" button does. The three modules all hook into `desktop.rs` (field, render call, `blocked()`), so their tasks run in sequence.

Review fixes to D7: (a) **Offline views.** `info_panel::body` and `profile::body` take the connection: a loaded list or profile is shown only while `ConnectionState::Online`; in any other state (Offline, and Connecting while a reconnect runs) a `Ready` state renders the offline notice, so an answer that arrives after the drop is never painted and nothing already on screen outlives the drop. The store keeps the loaded value (the dialog needs the own guid from the profile). When the connection returns, `Desktop::resume_reads` asks again for the open panel or profile (state `Ready` or `Failed { offline: true }`), which sets `Loading` and so never shows the earlier data as current; the core announces a connection state only when it changes, so this runs once per reconnect. (b) **Cancel while in flight.** The spec scenario "Cancel" is limited to before "Создать" and a scenario "Cancel after confirming" records the decision: a request that left cannot be recalled, so "Отмена" and Escape are inert until the outcome is shown; closing early would hide an unknown or unverified result or open a chat the user believes cancelled. The alternative (close at once and surface the outcome as a toast) was rejected as less honest and not cheap to make safe.
Alternative for candidates: a directory search. Rejected for this change (proposal decision 7).

### D8. Developer guard and live verification
When `BT_WRITE_ONLY_CHAT` is set, `YandexBackend::create_*` refuses with `Failed(Rejected { permanent: true })` and logs the attempt (kind only): the variable limits writes to one existing chat, and creation writes outside it. VM runs always set it, so they verify the refusal; a real creation through the app happens only in a task that unsets it with the user's approval.
`bt-probe` gains read commands `whoami` and `members <chat>` (task 1.2) and `create-private <guid> --confirm-create` (task 2.2; refuses without the flag and prints what it is about to create); `create-chat <title> <guid>... --confirm-create` arrives with task 6.1 if the gate passes. Output prints structure and names but never cookie or token values; fixtures recorded from live replies are sanitised (no cookies, no personal data beyond display names replaced by placeholders).

### D9. Sibling changes and merge order
`add-message-reactions`, `add-media-download` and `add-global-search` are being planned in parallel and may also touch `request.rs` (allowlist), `client.rs` (engine), `store.rs`/`desktop.rs` and the "Writes only from user actions" requirement of `message-sending`. Rule for every task here: edit by adding (new enum variants, new modules, new list entries) and extend the exact-list tests instead of replacing them; before editing a shared file read its current content. Archive order decides which delta is applied last; the later one re-reads the main spec and reapplies its wording.

### Task 1.2: `whoami` and member reads (live, read-only, 2026-11-24)

Run with `bt-probe whoami` and `bt-probe members <chat> [--method chat|group]` on the real account (44 private chats, 70 groups of 2 to 58 members, 2 channels, the self chat). The probe sends the task 1.1 bodies (`{"chat_id": <chat>}` only). Parameter experiments used a throwaway local patch that merged extra keys into `params`; it is not committed (task 1.3 owns `request.rs`). Fixtures: `live-whoami.json`, `live-members-group.json` (four users picked from different group replies to cover every key seen, in one reply envelope), `live-members-private.json` (the refusal body); all names, emails, positions, department and organization names, avatar ids, guids and uids are placeholders.

**`whoami`** (socket). Top-level keys `CurrentTime` (µs), `UserInfo`, `UserStatusInfo`. `UserInfo`: `AccountCategory`, `AccountType {Found, Value}`, `AvatarId`, `DiscoveryInfo {Restriction}`, `DisplayName`, `Email`, `Gender`, `Guid`, `IsConnect`, `IsLegal`, `IsOnboarded`, `Nickname`, `OrganizationInfos[] {AvatarId, OrganizationId, OrganizationName, RegistrationStatus, Rights}`, `PublicName`, `RegistrationStatus`, `Uid`, `Version`. `UserStatusInfo` is `{ "Timestamp": <µs>, "UserStatus": {} }`: **`UserStatus` is an empty object when no status is set** (the account has none); this is the only live observation, a populated status was never seen. Static path (web bundle 3.6.3, `app.js`): the whoami normalizer (`e2`) passes `UserStatusInfo.UserStatus` (or `{}`) into `e0(guid, timestamp, status, now)`, which reads `Availability`, `NotificationMode`, `Duration` and, when present, `CustomStatus.Emoji`, `CustomStatus.Text`, `CustomStatus.Localizations`, `CustomStatus.IconName` (PascalCase, unlike the request keys of `set_user_status`, which are `availability`, `notification_mode`, `text`, `emoji`). So the statically verified status text path is **`UserStatusInfo.UserStatus.CustomStatus.Text`**, not `UserStatus.text`. The parser in 1.3 takes that field when it is a non-blank string and treats everything else (including `{}` and a missing `CustomStatus`) as no status text.

**`get_chat_members` on a group** (registry, HTTP 200, no CSRF token sent: the route stays `csrf: false`, no `bad_csrf_token` was ever seen).
- Reply: `{ "users": [...], "groups": [], "departments": [] }`, no other key: **no paging marker and no total**. `groups` and `departments` were empty in all 70 groups, so their element shape is unobserved (the web client passes them through as arrays).
- User keys always present: `account_category` (1 or 2), `display_name`, `guid`, `public_name`, `registration_status` (`U` or `Lu`), `role`, `version`. Sometimes present (of 353 users sampled): `avatar_id` (297), `contacts[] {default, organization_id, type: "email", value}` (327), `employee_info {deleted?, department {id, name}, display_name, is_admin, organization_id, position}` and `employees_info[]` (same plus `organization_name`; 306), `gender` (`male`/`female`; 349), `is_connect` (305), `phone_id` (127); rarely: `account_type {found, value}`, `email`, `is_onboarded`, `mcrm_registration_ts`, `nickname`, `uid` (13 each), `account_deleted` (1). `display_name` is always present, so names need no `get_users_data` round trip for this reply; `avatar_id` is the usual `user_avatar/yapic/...` id.
- `role` values: **`admin`, `member`**; every user had one. `subscriber` appears only in the web client's role filter for channels. A group may have several admins (up to 10 seen). Admins are listed first on the default page, but order is not guaranteed (a page with `expand_groups` started with a member), so the parser must not rely on it. The signed-in user is in the list.
- Paging and page size: without `limit` the server returns **20** users (one admin and 19 members in the group probed). `limit` is honoured as a positive integer up to at least 1000 (a 58-member group came back whole at 100 and at 1000); a `limit` of 0, a negative one or a string is ignored (default 20). The web client asks for 50. The next page is `guid_offset: <guid of the last user of the previous page>` (pages did not overlap); an offset past the end gives an empty `users`; an unknown guid is ignored and returns the first page again. There is no "more" flag: a page shorter than `limit` is the last one (the web client tests `users.length >= 50`). Admins count against `limit` when `roles` is absent.
- `roles` filter: `["admin"]` and `["member"]` work (the web client loads admins and members separately and merges them); an unknown role is `bad_request`.
- Other parameters the web client sends: `expand_groups: true` is accepted (same users here), `groups_only: true` returned no users, `invite_hash` was not tried.

**Chats that refuse `get_chat_members`**: two private chats and the self chat, and both channels (with and without `roles: ["subscriber","member"]`): **HTTP 403** with `{"status":"error","data":{"code":"no_permissions_for_this_chat_operation","text":"","source":"yamb"}}` (`live-members-private.json`). So: `get_chat_members` does **not** work for private chats (the partner comes from the chat row, as D1 already allows); for channels it is refused for this account, probably because it is not an admin of those channels [INFERENCE], so the panel needs a "list unavailable" state for channels.

**`get_group_members`**: `bad_request` for a group, a channel and a private chat, with `chat_id` alone, plus `limit`, plus `roles`, and with a `group_id` key; the web bundle defines it in its API class but no UI code calls it (it is probably the member list of a directory group, not of a chat). It is of no use for this change.

**Where each finding lands** (applied to the artifacts by the spec-reconcile pass; code owners follow the tasks):
- 1.3 (`request.rs`, `client.rs`, `wire.rs`): `ReadRequest::ChatMembers` carries `{chat, limit, guid_offset: Option<guid>, roles: Option<..>}` and builds `{"chat_id", "limit", "guid_offset"?, "roles"?}`; `GroupMembers` is dropped (allowlist 8 → 7 names, the pinned tests in `request.rs` and `write.rs` follow) unless a later live check finds a working shape; `Client::members_raw(chat, kind)` becomes a paged typed `members(chat, limit, guid_offset)`; `WireMembers` has no paging marker, `partial` is derived by the caller (D1, D6).
- 3.1 (backend): members are loaded for `ChatKind::Group` and `ChatKind::Channel` (a channel refusal is a failed load saying the list is not available); a private chat is shown from the chat row without a request. Pages of 50 with `guid_offset`, bound of 20 requests (1000 members); `partial` is set when the bound is reached with a full last page (D6).
- Specs: `chat-members` states what the panel shows per chat kind (group: server list; private: partner from the chat row, no member request; refused list: "not available to this account"), replaces the "server says more exist" wording of the partial-list requirement with the real paging rule (no total, no flag), and covers the empty `UserStatus` and profile errors; `chat-creation` names groups (not any chat) as the source of members in the participant picker.

## Risks / Trade-offs

- [Creation acts on the real account and cannot be undone by this client] → closed mutation set (D2), confirmation dialog (spec), `--confirm-create` flag in the probe, `BT_WRITE_ONLY_CHAT` refusal (D8), live runs only with approval.
- [A duplicate chat after a lost reply] → no automatic retry, outcome classification (D3), existing private chat opened instead of created (D5); group duplicates remain possible and are left to the user, who is told the result is unknown.
- [Parameters of the member reads and the creation calls are partly inferred] → shapes recorded from live reads first (1.2), parsers tolerant like `parse_users`, tests on recorded fixtures; the group gate (D4) and the private-chat fallback (D2) take unverifiable parts out of the change instead of shipping them.
- [`get_chat_members` does not work for private chats, the self chat and (for this account) channels; `get_group_members` is unusable] → resolved by task 1.2: private chats are shown from the chat row, a refused channel list is shown as not available to the account (the cause, probably that the account does not administer those channels, is an [INFERENCE]), `get_group_members` is dropped (D1).
- [Large groups: no total, no "more" flag] → pages of 50 until a short page, bounded at 20 requests; `partial` marker and bounded loading (D6); the panel never presents a cut list as full.
- [Status text semantics unknown] → shown verbatim only when present (D6); no presence claims.
- [Shared files collide with the three sibling changes] → additive edits, exact-list tests extended, read before editing (D9).
