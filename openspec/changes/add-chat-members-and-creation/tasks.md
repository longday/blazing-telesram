# Tasks

Each task names the files it owns and what it depends on. Tasks without a dependency between them may run in parallel; a task shares files with every task that edits the same file, so those run in order. Streams that are independent of each other: **P1** (1.x), **P2** (2.1, then 2.2 after 1.3), **G** (0.1). After 3.1 the core stream **C** (3.2 → 3.3) and the UI stream **U** (4.x) overlap as marked. Tasks marked `[approval]` act on the real account and need the user's explicit approval of the target before they start; without it they stay open and block only the archive, not the implementation. Decisions D1–D9 are in `design.md`.

## 2. Protocol creation (`yandex-proto`, stream P2)

- [x] 2.1 New closed mutation module per D2 and D3: `ManageRequest::CreatePrivateChat { guid }`, `MANAGE_METHODS`, `RegistryClient::manage` (always CSRF, shared cookie/header code, `ManageError::{NotSent, Rejected, Unknown}`), tolerant reply parser returning `Option<chat id>`. Files: `crates/yandex-proto/src/manage.rs` (new), `crates/yandex-proto/src/registry.rs`, `crates/yandex-proto/src/lib.rs` (`mod manage` and re-exports). Depends: none. Verify: stub-server tests in `registry.rs` for success with and without a chat id, `status` not ok → `Rejected` with the code, 401 → `Rejected(SessionExpired)`, 5xx and hang → `Unknown`, CSRF failure → `NotSent`, the CSRF header present, and no cookie or token in the log output; `manage.rs` tests that the method list is exactly `MANAGE_METHODS`, disjoint from `ALLOWED_METHODS`, and that none of `change_chat_members`, `change_chat_role`, `change_chat_admins`, `leave`, `invite`, `invite_renew`, `set_chat_info`, `create_token` is representable.
  - Done. Decisions: `manage` classifies in this order: CSRF exchange failure (any `ProtoError`, including a 401/403 there) → `NotSent`; connection that never opened (`reqwest::Error::is_connect`) → `NotSent`; any other transport failure after the request left (timeout, reset, body read) → `Unknown`; HTTP 401 → `Rejected(SessionExpired)`; HTTP 429/5xx → `Unknown` even with a JSON error body (the server may have acted before failing); a non-JSON body → `Unknown`; `status` not `ok` → `Rejected` (cookie codes → `SessionExpired`, else `Protocol("create_private_chat failed: <code>")`, `unknown` when no code); `status: "ok"` → success with `data`, or `Json::Null` when the reply has none. `created_chat_id(data)` tries `/chat_id`, `/chat/chat_id`, `/chat/id`, `/id` (shape unconfirmed until task 5.1) and returns `None` otherwise. `manage` and the re-exports are `pub` so the crate has no dead code before 2.2 adds the facade. The log test registers a second tracing dispatcher: with one, tracing builds callsite interest from a thread default that `set_default` has not installed yet, so a callsite another test already hit stays disabled for the capture (it failed in `cargo test manage`); `test_log.rs` has the same latent weakness for its other users.
  - Redirects: `RegistryClient` holds a second client, `mutation_http`, with the same deadlines and `redirect::Policy::none()`, used only by `manage` (the CSRF exchange keeps the default client). A redirect after the creation POST left is therefore a non-success reply (non-JSON body → `Unknown`), never a failed second connection that would read as `NotSent`; regression `manage_never_follows_a_redirect_after_the_request_left`.
