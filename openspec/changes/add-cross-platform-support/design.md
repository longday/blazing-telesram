# Design: add-cross-platform-support

## Context

The workspace has three crates: `yandex-proto` (wire, session, `bt-probe`), `chat-core` (client engine, cache, downloads) and `desktop` (GPUI app, the only crate with a UI). Today only macOS builds. `research.md` Part 1 is the inventory (hard compile errors, then macOS behaviour that compiles); Parts 2 and 3 are what GPUI 0.2.2 and `wry` 0.57.3 provide on Linux and Windows; Part 4 is the audio record; Part 5 is Windows file-system facts; Part 6 is how each platform is verified from this Mac.

Constraints: macOS behaviour and its tests stay as they are; no stub, no no-op arm, no `#[allow(dead_code)]`, 0 warnings (rules 2 and 3 of `DEPENDENCIES.md`); no hand-written codec or crypto (third-party crates only, each with its licence in `THIRD_PARTY.md`); cargo only in a VM; no CI change; credentials (cookies) never reach a log, an argument list or an environment variable; the UI replicates Telegram Desktop's look, so nothing here changes pixels except where a platform forces it (the Linux title bar, D6).

**Goals:** `run-linux.sh` and `run-windows.ps1` produce a window that signs in, lists chats, opens history, sends, downloads, plays a voice message, and keeps its secrets owner-only, with the same behaviour as macOS apart from the stated differences. Workspace compiles for `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` and `x86_64-pc-windows-msvc`.

**Non-goals:** see `proposal.md` (packaging, CI, other targets, cookie paste, Mark-of-the-Web).

## Decisions

### D1. Shape: one policy for platform code

- **Pure logic is platform-neutral and compiled and tested everywhere.** Only the thin adapter that calls an OS API is `cfg`-gated. A module that only non-macOS builds use is declared `#[cfg(any(not(target_os = "macos"), test))]`, so the macOS gate compiles and tests it and no `dead_code` warning appears in a macOS non-test build (the module is absent there). Example: the sign-in helper protocol (D7), `windows_safe_name` (D3), the key tables (D5), the Opus decode loop (D8).
- **Backends hide behind the existing seams.** `AudioOutput`/`AudioFactory` (`player.rs:25-49`), `DockBadge` and `Platform`/`AlertsFactory` (`alerts.rs`, plus `Notifier` from NB-N), `cx.open_with_system`, `cx.reveal_path`. `main.rs` registers the backend of the current OS; there is no `match`-with-empty-arm anywhere.
- **No "unsupported platform" stubs.** A seam with nothing to offer on a platform is an absent value with a real, user-visible outcome, never a placeholder: no `AudioFactory` means `NoOutput`; in alerts `Platform.badge` and `Platform.notifier` are **each** an `Option` and are `None` **independently** (Linux: a notifier and no badge; a desktop whose notification service is unreachable: no notifier). `Alerts` serves whichever is present (D10); a missing badge never disables notifications.
- **Desktop does not compile off macOS until the last backend lands.** Each unit adds its non-macOS backend and its `cfg` gate together; `desktop` becomes buildable on Linux and Windows when XP-S, XP-P and XP-W are all on `main` (the `integ/cross-platform` branch is the first place it is whole). Libraries (`bt-platform`, `yandex-proto`, `chat-core`) compile on every target from XP-A on, and that is checkable at once (D11). This is why the spike S0.2 runs on a scratch copy.

### D2. Private storage: `crates/platform` (`bt-platform`)

Three crates need the same thing and `chat-core` does not depend on `yandex-proto`, so a leaf crate is the smallest honest home. It has no dependencies on the other workspace crates. API (names fixed at apply time with `lsp` references on every call site; behaviour fixed here):

- `create_private_dir_all(path)`: creates `path` and every missing ancestor owner-only (`0700` on Unix, as `DirBuilder::recursive(true).mode(0o700)` does today: only directories the call creates get the mode, existing ones are left alone).
- `ensure_private_dir(path)`: the existing-directory case of `prepare_playback_dir` and `open_log_file` (`set_permissions(0o700)`): brings an existing directory the app owns to owner-only.
- `open_private_file(path, mode)` with the modes the call sites use today (`create` without truncate, `create_new`, `create_new` + append, truncating create): the file is owner-only **from the instant it exists** (Unix: `mode(0o600)` at `open`; Windows: `CreateFileW` with a `SECURITY_ATTRIBUTES` that carries the descriptor, so there is no window with an inherited ACL). `chmod` after the fact (`cache.rs:113`) stays on Unix and has the Windows equivalent in `ensure_private_file`. The crate offers only private creation: a file that must **not** be private (an ordinary download, D3) is made with plain `std::fs::OpenOptions`, so the two kinds are never confused.
- `is_owner_only(path)`: for `bt-probe check_sample_dir` and for the tests that assert modes today (`mode & 0o077 == 0`; on Windows: the DACL is protected and has exactly one allow entry, for the current user).
- `rename_no_replace(from, to)` (Linux and Windows only; macOS keeps `hard_link`): an atomic rename that fails with `AlreadyExists` when `to` exists and with `Unsupported` when the file system cannot do it; the single place for the `unsafe` FFI (`renameat2` through `libc`, `MoveFileExW` through `windows`), used by `chat-core` `commit_partial` (D3).
- **Windows descriptor.** SDDL `D:P(A;OICI;FA;;;OW)`: protected (no inherited entries), one allow entry for `OW` = OWNER_RIGHTS, a well-known SID that stands for **whoever owns the object at the time of the check**, not for the creating account. It needs no SID lookup. The owner of a new object is the creator's user SID by default, but a process that runs elevated may create objects owned by the **Administrators group** (policy "default owner"), and then the entry grants every administrator; likewise an owner change moves the access. So the claim is "only the owner of the object", which equals "only the current user" in the normal, non-elevated run, and it is **not** a defence against an administrator (who can take ownership anyway), against SYSTEM, or against other processes of the same user. S0.6 tests a normal and an elevated process; if the elevated case shows the group, or `OW` misbehaves for a file or a directory, the descriptor uses the current user's SID from the process token instead (same SDDL with the SID). Applied through `ConvertStringSecurityDescriptorToSecurityDescriptorW` and `SetNamedSecurityInfoW`/`CreateFileW`, using the `windows` crate at the version GPUI already resolves (`windows` 0.61 in `Cargo.lock`, features `Win32_Security`, `Win32_Security_Authorization`, `Win32_Storage_FileSystem`; the exact set is found by `cargo check --target`), so the lock gains no second copy of it. SYSTEM and administrators lose their access entry; no backup tool is expected to read these files. On Unix the same limit holds: root and the same user's other processes can read `0600` files.
- The only `unsafe` in the new crate is the FFI around those calls, each block with a `SAFETY:` comment; the Unix half uses only safe `std::os::unix` extension traits.
- **Not done:** the runtime directory the user points `BT_RUNTIME_DIR` at is not rewritten (as on Unix, where `run.sh` makes it `0700` and the app does not chmod it). `run-windows.ps1` is the other agent's file; the app protects every directory and file it creates **inside** it, which is what holds the secrets (the session, the cache, the media, the logs). `docs/platforms.md` says so.

Call sites that change (all become calls to `bt-platform`; the tests that import `PermissionsExt`/`MetadataExt` use `is_owner_only`): `session.rs:4,79-109,135,195`, `bt-probe.rs:1135-1147,2277-2280`, `cache.rs:14,105-113,568,1059`, `client.rs:18,593-603,3048-3055`, `paths.rs:6,159-167`, `logging.rs:9,124-145,194,304-305`. **Unix-only tests, all of them** (found by a search for `os::unix`, `PermissionsExt`, `OpenOptionsExt`, `DirBuilderExt`, `MetadataExt`, `symlink(`, `.mode(`, `from_mode`): `client.rs:8103` (`mode_of`), `8467`, `8469`, `8506`, `8509`, `8540`, `8629`, `8658` (`std::os::unix::fs::symlink`), `8590-8593` (a `0o755` folder through `DirBuilderExt` and `from_mode`), `paths.rs:355-358,431`, `session.rs:135,195`, `cache.rs:568,1059`, `logging.rs:194,304-305`, `bt-probe.rs:2277-2280`. Rule: a test either goes through `bt-platform` (modes become `is_owner_only`) or is `#[cfg(unix)]` **with a Windows counterpart that needs no privilege** (creating a symlink on Windows needs a privilege or developer mode). The symlink refusals ("the playback or account path is not a plain folder") get a counterpart that puts a **regular file** where the folder should be, which `require_plain_dir` rejects the same way. The widened-folder test (`0o755`, `client.rs:8580-8597`) is `#[cfg(unix)]`; its Windows counterpart creates the folder with the inherited, unprotected access and asserts that `ensure_private_dir` makes `is_owner_only` true (run by 8.3). `check_sample_dir` is tested through `is_owner_only`. Two more facts: `main.rs:322-323` passes `/Users/me` to the pure `downloads_dir`, whose `is_absolute()` is false for that string on Windows, so that function and its tests are `cfg(target_os = "macos")` (Windows and Linux use `dirs`, D3); `tests/probe_write_guard.rs` already skips itself off macOS (it needs `/usr/bin/sandbox-exec`) and **runs no probe on Linux or Windows**, which is stated as not covered there. `require_plain_dir` (`symlink_metadata().file_type().is_dir()`) already rejects any reparse-point symlink and junction in production.

### D3. Paths and names

- **Downloads folder.** `downloads_dir` (`main.rs:171-176`) keeps its macOS rule (`$HOME/Downloads`, absolute, unchanged tests). On Windows and Linux it uses the `dirs` crate (`download_dir()`: the known folder `FOLDERID_Downloads` on Windows, which survives a redirected folder; `XDG_DOWNLOAD_DIR` from `user-dirs.dirs` on Linux, which is `~/Загрузки` on a Russian desktop). `dirs` is already in `Cargo.lock`. The result is validated as an absolute path exactly as today; a missing folder is the existing «Downloads folder unavailable» outcome. The pure part (`home -> path`) stays unit-tested on macOS; the platform part has one test per OS.
- **File names.** `sanitize_file_name` keeps its behaviour on macOS. A pure `windows_safe_name(name)` (compiled and tested everywhere) maps `<>:"|?*` and control characters to `_`, strips trailing dots and spaces, and prefixes `_` to a reserved device stem (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, case-insensitive, with or without an extension). It is applied by `cfg!(windows)` inside `sanitize_file_name`, so every caller (`create_partial`, `commit_partial`, which both sanitise again) is covered. Linux needs nothing beyond what exists: `/` and NUL are already removed.
- **Claiming the final name.** The existing requirement "Complete or absent" (`attachment-download`) and the archived `add-media-download` design (Decision 5: "no fallback to `rename`, which could overwrite"; a failed claim fails the download with `Disk`) stay in force. A copy into the final name would expose an empty or half-written file under it and leave it behind when interrupted, so **there is no copy fallback**. `commit_partial` claims the name only by an atomic operation that fails when the name exists: macOS: `fs::hard_link`, unchanged. Windows: `bt-platform::rename_no_replace`, i.e. `MoveFileExW(partial, final, 0)` without `MOVEFILE_REPLACE_EXISTING` (atomic on one volume, refuses an existing target, and works on FAT/exFAT and SMB where hard links do not; `std::fs::rename` is not used because it replaces). Linux: `rename_no_replace` through `renameat2(RENAME_NOREPLACE)` (ext4, btrfs, xfs, tmpfs, overlayfs); if the file system answers that the flag is unsupported (`EINVAL`/`ENOSYS`: vfat, exFAT, some NFS/FUSE) the claim tries `hard_link`; if that fails with anything but `AlreadyExists` too, the download fails with `Disk` as it does today, the partial is removed by its guard, and nothing is ever written under the final name. `AlreadyExists` still moves on to `name (1).ext`. The partial's file handle is closed before the claim (Windows refuses to rename an open file; the code already drops it before `commit_partial`). On macOS the behaviour is unchanged. Tested with an injectable claim function (every OS) and the real functions on Linux (VM) and Windows (8.3).
- **Two kinds of partial file.** `create_partial_with_mode` serves two callers with two modes (`client.rs:773`): the playback copy (private, `0600`) and an ordinary download (`0666` before the umask, the user's usual file mode). **Both stay in the API**: the mode becomes a two-valued argument (`PartialMode::Private` and `PartialMode::Ordinary`; the name is fixed at apply), and `create_partial` is `Ordinary`. `Private` goes through `bt-platform` (`0600` at `open`; the protected DACL on Windows). `Ordinary` uses plain `OpenOptions::create_new` on every OS: on Unix `0666 & !umask` as today, on Windows the access the Downloads folder gives (inherited), which is what any browser's download gets. An ordinary download is **never** made private: it is the user's file, which other tools of the same user (and a backup) must read. Tests (every OS where it can be asserted): the playback partial is private from creation; on Unix an ordinary partial has `0o666 & !umask` (the test reads the process umask and compares); on Windows `is_owner_only` is false for an ordinary partial in a folder with inherited access (8.3).
- **Local UTC offset** (`format.rs:60-82`). Unix keeps `localtime_r`. Windows uses the UCRT: `_localtime64_s` and `_mkgmtime64` (the offset is the difference of the two), two `extern "C"` declarations with a `SAFETY:` comment, no new crate (`c_long` is 32 bit there, so the struct is declared with `i32` fields for Windows). The function is the same pure signature; a test compares it with `TZ`-set known zones on Unix and with the system zone on Windows.
- **`std` limits accepted:** long paths (`std` adds `\\?\` itself), case-insensitive names (the unique-name loop already handles it on macOS).

### D4. Cargo: target-gated dependencies

`crates/desktop/Cargo.toml`: `block2`, `objc2`, `objc2-app-kit`, `objc2-avf-audio`, `objc2-foundation` (and, from NB-N, `objc2-user-notifications`) move under `[target.'cfg(target_os = "macos")'.dependencies]` with the pinned `=` versions unchanged. New dependencies: `ogg` and `ropus` for every target (pure Rust; macOS compiles them for the tests of the pure decode loop, D1, and does not link them into its non-test build); target table `cfg(not(target_os = "macos"))`: `rodio` (with `cpal`), `dirs`, `tao`; `cfg(target_os = "windows")`: `windows`; `cfg(target_os = "linux")`: the notification crate of D10. `wry` stays unconditional (macOS: the in-process view; elsewhere: the helper). `gpui` keeps `runtime_shaders` if S0.2 shows it is inert elsewhere, else it moves to a macOS-only second declaration of the dependency (Cargo unifies the features). All versions are pinned with `=` like the existing ones; `Cargo.lock` is updated once per unit, with `--locked` builds after.

Linux system packages (documented in `docs/platforms.md`, installed by the user): `build-essential pkg-config libssl-dev libwebkit2gtk-4.1-dev libgtk-3-dev libasound2-dev libxkbcommon-dev libxkbcommon-x11-dev libwayland-dev libx11-xcb-dev libxcb1-dev libfontconfig1-dev libvulkan1 mesa-vulkan-drivers xdg-utils fonts-noto-core fonts-noto-color-emoji` (the final list is the output of S0.2/S0.5, not this guess). Windows: Visual Studio Build Tools (MSVC and a Windows SDK), the WebView2 Evergreen runtime. No `cmake`.

### D5. Shortcuts

- Replace the pairs and singles in `main.rs:68-76` and `input.rs:1028-1040` by one table per platform family in a pure module (`keys.rs`): on macOS the current bindings exactly (`cmd-*` plus the existing `ctrl-*` duplicates); on Linux and Windows the `ctrl-*` forms: `ctrl-f` Search, `ctrl-shift-l` ToggleLog, `ctrl-a/c/v/x/z` in the text input (those already exist as duplicates), `home`/`end` and `ctrl-left/right` for word moves only where the macOS table has `cmd-left/right`/`alt-left/right`, `ctrl-q` Quit on Linux (Q6). `ctrl-cmd-space` (character palette) is bound on macOS only.
- Code that checks a modifier uses `Modifiers::secondary()` (macOS Cmd, elsewhere Ctrl) instead of `platform()`. `add-text-selection-and-quotes` (on `main`) already does: its `secondary-c`, `secondary-a` and `Modifiers::secondary()` Cmd+click are right on every platform; only the table of `keys.rs` has to include its bindings (`tasks.md` 2.1 and "Overlaps").
- Tests simulate `secondary-<key>`, which GPUI resolves to Cmd on macOS and Ctrl elsewhere; on macOS they therefore run the very same keystrokes as today. **Every** `cmd-` in the tests moves, found by a search for `cmd-` and for `"cmd` in `tests.rs`, `input.rs`, `main.rs`: `cmd-a` (`tests.rs:777,830,1881,1903,1917,2212,2302,2386`), `cmd-shift-l` (`tests.rs:1679,1688`), and the helper `with_log_shortcut` with its four callers and their keystrokes (`tests.rs:2824-2847,2868-2872,3166-3174,3219-3232`), whose `KeyBinding::new("cmd-shift-l", ..)` must take the binding from `keys.rs` instead of repeating it. After the change a search for `cmd-` finds it only in the macOS table of `keys.rs` and in the test that pins that table.
- The spec text names «Cmd+Shift+L» (`diagnostic-log`): it becomes "the platform's primary modifier + Shift + L" (macOS Cmd, Linux and Windows Ctrl).

### D6. Window, fonts, Linux title bar

- **Fitting.** `fitted_window_bounds` (`main.rs:248-272`, used by `login.rs:126` too) keeps its AppKit body on macOS (`cfg`). Elsewhere it centres the preferred size inside `display.bounds()` shrunk by a fixed margin (the task bar and a title bar are not in `bounds()`, `research.md` Part 2): the preferred size is clamped to the display minus 96 px of height and 32 px of width. A pure function takes the preferred size and the display size and is tested everywhere; the adapter reads the display from `cx`.
- **Log font.** `.font_family("Menlo")` (`desktop.rs:1923`) becomes a per-platform constant: «Menlo» macOS, «Consolas» Windows, «DejaVu Sans Mono» Linux, with `font_fallbacks` to the others, so a missing face degrades to a monospace face, not a proportional one.
- **Text and emoji.** The default family `.SystemUIFont` is unchanged. Cyrillic and colour emoji (the reaction chips) depend on installed fonts; `docs/platforms.md` lists `fonts-noto-core` and `fonts-noto-color-emoji` for Linux. S0.5 checks what the fallback stack finds on Ubuntu with and without them; if reaction emoji render as boxes without the package the doc says so, and the app logs one warning at start naming the missing family (no font data is embedded: licences, size).
- **Linux title bar.** GPUI asks for server decorations; on Wayland compositors without an xdg-decoration server (GNOME) the window gets `Decorations::Client` and nothing is drawn, so it cannot be moved, resized or closed. When the window reports `Decorations::Client`, a `window_chrome.rs` draws a 32 px title bar in the theme (title text, minimise, maximise/restore, close), starts a move on a drag of the bar (`start_window_move`), a maximise on double click (`zoom_window`), and an invisible resize band of 6 px at the edges and corners (`start_window_resize`), reading `window_controls()` to hide buttons the compositor does not allow and setting `set_client_inset`. When the window reports `Decorations::Server` (X11, KDE, Windows) nothing is drawn. This is the one place where Linux pixels differ from macOS; S0.5 confirms the mode in a headless Wayland compositor and with X11, and a real GNOME check is **[needs-user]**.

### D7. Sign-in on Linux and Windows: a helper process

**Why not in-process.** (a) Linux: `wry`'s `build_as_child` works only for an Xlib handle (research Part 3); on Wayland WebKitGTK needs a GTK container, GTK must be initialised and its main loop pumped, `cookies()` itself spins `gtk::main_iteration()`, and GPUI's `calloop` loop does not pump GTK. A GTK widget cannot be parented into a GPUI Wayland surface. (b) Windows: a WebView2 child of a GPUI DirectComposition window is untested. (c) The macOS path works and is left alone.

**Shape.** The same executable, started with the single argument `--sign-in-helper`, handled at the very top of `main()` **before** logging, runtime directory, GPUI or the log file are touched (it must not rotate the logs or need `BT_RUNTIME_DIR`). `cargo run -p blazing-telesram` builds one binary, so there is no second `[[bin]]`.

- **Helper.** A `tao` event loop with one top-level window (title «Вход в Яндекс», sized by `fitted_window_bounds`'s pure part) and an incognito `wry` view on `https://telemost.yandex.ru/` with the same new-window handler as `login.rs` (a window request is loaded in the same view; the origin helper `origin` is used for any log text, never the full URL). On Linux, `wry`'s `build_gtk` on the `tao` GTK window; on Windows `build` on the window. Every second it asks `webview.cookies()` (on Linux that call pumps GTK itself) and, as soon as `has_session(cookies)` (the existing predicate: a `Session_id` cookie for `yandex.ru`), prints **one line of JSON** (`{"cookies":[...]}` in the existing `LoginCookie` shape) to stdout, flushes, and exits 0. Window closed by the user: exit 3, nothing printed. Web view could not be created: exit 4 and one fixed word on stderr (`webview-unavailable`, `gtk-unavailable`); no URL, no cookie, no OS error text is ever printed (those can contain paths or tokens). A reader thread on **stdin** treats EOF as "the app is gone": it posts a quit to the event loop, so an app that crashes or is killed does not leave a sign-in window behind.
- **App.** `open_sign_in` (`main.rs:127`) on these platforms opens a small GPUI window «Ожидание входа в браузере…» with **Отмена**, spawns the helper (`current_exe()`, piped stdin and stdout, stderr piped, no inherited handles, a `Drop` guard that kills it), and reads its stdout on a thread. Exit 0 with valid JSON: the cookies go through the existing `verify` and `Session::save` path, the waiting window closes and the chat window opens (identical to today after `on_cookies`). Exit 3 or Отмена or closing the waiting window: kill the helper and quit the app without storing anything (today's «User closes the sign-in window»). Exit 4 or a spawn failure: the waiting window shows «Не удалось открыть окно входа: <what to install>» (a fixed text per code) and Закрыть quits. Verification failure: as today.
- **Secrets.** The cookies travel over an anonymous pipe only: never in argv, the environment, a file, a log or `Debug` output (`LoginCookie`'s redacting `Debug` is kept; the protocol type has none that prints values). The app logs the helper's exit code (a number) and nothing else. **What this does not do:** the pipe keeps the cookies out of places other users and log readers can see; it does **not** isolate them from other processes of the same user, which can read the app's or the helper's memory or `/proc` entries where the OS allows (ptrace scope, debug privilege), exactly as they can read the stored session file. The session file's protection (D2) is the same kind: against other accounts, not against the same user or an administrator.
- **Missing system libraries.** `wry` is linked into the one binary on every platform, so on Linux a missing `libwebkit2gtk-4.1` stops the process in the dynamic loader **before `main`**: the app cannot print anything and the exit-4 path of the helper cannot run. For a run from source this cannot happen after a successful build, because the build needs the `-dev` packages and fails with a `pkg-config` message that names a `.pc` file, not a package to install. The plan does not split the loading (a second binary or a `dlopen` of WebKitGTK would break the one-`cargo run` shape of the run scripts); it puts a **preflight in `run-linux.sh`** (task 8.5): before `cargo` it runs `pkg-config --exists` for the modules the build needs (`webkit2gtk-4.1`, `gtk+-3.0`, `alsa`, `openssl`, `xkbcommon`, `wayland-client`, `fontconfig`), prints the install line for the missing ones (the Debian/Ubuntu names of D4; other distributions are not verified, Q3) and exits non-zero without starting cargo. The run scripts are on the branch `docs/readme` and belong to its author until it is merged; 8.5 starts only after that. On Windows the WebView2 loader is linked statically (`WebView2LoaderStatic`; S0.2 confirms with `dumpbin /dependents` that the binary needs no extra DLL), so a missing runtime is a runtime error of the helper (exit 4 and the fixed text «Не удалось открыть окно входа: установите WebView2 Runtime»); it is tested through the exit-code path of 3.3 and seen on a real machine only if the user has one without the runtime.
- **Pure parts compiled on macOS too:** the protocol (`encode`/`decode` of the cookie line, the exit-code mapping, the fixed stderr vocabulary) and the cookie predicate, tested without a window (round trip; a line with a bad JSON; a value never appears in `Debug`). `login.rs`'s `LoginCookie`, `convert_cookie` and `has_session` move to a platform-neutral module used by both.
- **What is not decided in advance:** which `tao` version (the one `wry` 0.57.3 is compatible with, `cargo tree` in the VM) and whether Linux uses `tao`'s GTK window or plain `gtk`; S0.3 decides.
- Cost accepted: on Linux and Windows the sign-in is a window of its own, not a pane of the chat window; the first launch looks different from macOS. After sign-in the helper is gone and nothing web-related runs.

### D8. Voice playback on Linux and Windows

Implements `AudioOutput` (`open` returns the exact length, `play`, `pause`, `stop`, `position`, `finished`) in a new `audio_pcm.rs` (name fixed at apply), registered by `AudioFactory` on `cfg(not(macos))`; `audio.rs` and `objc2-avf-audio` are macOS-only and unchanged.

- **Decode.** `ogg` reads the pages, `ropus` decodes every packet to PCM; the decoder stays the library (what is written here is container bookkeeping, RFC 7845, not a codec). The whole file is decoded in `open` into one buffer (a voice message is small: the longest observed is 566 s, which decodes in 0.5 s in release, MP R5). The header and the end are handled as the RFC says (§4.2 `OpusHead`, §4.4 end trimming) because MP R5 measured that a bare decode loop is **wrong** against Core Audio: **+48 frames** (1 ms) in 7 of 17 files and **+4368 frames** (91 ms, the last granule is shorter than the packets) in one. So: (1) read `OpusHead`: version, channel count (1 or 2; mapping family 0 only, anything else is `Unsupported`), **pre-skip** and output gain; (2) drop the first `pre_skip` decoded frames (all 17 samples have pre-skip 0, so a fixture with a non-zero one is required); (3) take the granule position `G` of the **last page**; the length is `G - pre_skip` frames and the buffer is **truncated to it** (a last page with no valid position, `-1`, or `G < pre_skip` falls back to the decoded count minus pre-skip; a file that decodes to **fewer** frames than `G - pre_skip` uses the decoded count); (4) the output gain of the header is applied; (5) more than one logical stream (a chained file) is `Unsupported`. The duration is that frame count over 48 000, which is how the macOS backend (`afinfo`'s estimate, equal to the granule rule to the millisecond in 17 of 17) and the spec define it; the server's `Duration` is not trusted (up to 280 ms longer). A file that is not Ogg Opus, or has zero frames, is `Unsupported`; one that cannot be read is `Io`.
- **Output.** `rodio` (no default features: no `symphonia`, no `lewton`) plays the buffer through `cpal` (WASAPI on Windows, ALSA on Linux, which reaches PulseAudio and PipeWire through their ALSA plugins). `rodio` converts mono 48 kHz to the device's channels and rate, so the app does no resampling. `play`/`pause`/`stop`/`position` map to the `Sink`; `finished` is "`play` was called and the sink is empty". A missing device is `NoOutput`.
- Why not `AVAudioEngine`-equivalents by hand or `symphonia`: MP R5 already measured them (`symphonia` has no Opus decoder in the released versions; `libopus` needs `cmake` on every machine); the decoder is the measured candidate C4, new crates are `ogg`, `ropus`, `wide`, `safe_arch`, `rodio`, `cpal` and what they pull in (S0.4 lists them with `cargo tree`; every licence goes into `THIRD_PARTY.md`).
- Pure and macOS-compiled: the decode loop over `ogg`/`ropus` with the header and end rules above, the length computation, the end detection. Fixtures (small binaries checked in under `crates/desktop/tests/fixtures/`, no speech: a tone, made once by a throwaway script outside the repository with `opusenc`/`ffmpeg` and, for the end cases, by rewriting a page's granule position and CRC in a scratch tool that is not committed; the expected frame counts come from the RFC rule and are cross-checked with `ffprobe`/`opusinfo` in the Linux VM): (a) pre-skip 312, last granule exact; (b) pre-skip 0 and a last granule **48 frames** short of the packets (the +48 case); (c) a last granule **4368 frames** short (the sample-10 case); (d) a last granule `-1`; (e) a non-zero output gain; (f) stereo; (g) a truncated file and a text file. Each test asserts the exact frame count and, for (a) and (e), a checksum of the PCM, so a missing pre-skip or gain shows. The `rodio` adapter is the only `cfg`-gated code.
- Video stays «open in the system player» (`cx.open_with_system`: `ShellExecuteW`, `xdg-open`), unchanged: `xdg-utils` is a Linux prerequisite.

### D9. Labels and the file manager

`REVEAL_LABEL` (`viewer.rs:105`, `timeline.rs:578`) becomes a function of the platform: «Показать в Finder» (macOS, unchanged), «Показать в Проводнике» (Windows), «Показать в папке» (Linux, where the file manager is not known). The tests (`tests.rs:10296`, `viewer.rs:470`) compare against the same function, so they hold on every OS. `cx.reveal_path` selects the file on macOS and Windows; on Linux GPUI goes through the portal and falls back to opening the folder: the spec says "shows the folder with the file selected where the platform can select it, otherwise shows the folder", and a missing file still reveals nothing and offers Download again. ### D10. Alerts

- **After NB-N.** NB-N adds `Notifier` and `Platform.notifier` and `notifier.rs` over `UNUserNotificationCenter`; its design says Windows and Linux are non-goals. XP-N adds the Linux and Windows `Notifier` implementations behind the same trait and the same `decide`/`notification_for` rules (the content, the muting and the window-state rules live in `alerts.rs` and are shared), registered by `cfg`. XP-N does not start before NB-N is on `main` (rule 1: `alerts.rs`, `main.rs`, `Cargo.toml`, `Cargo.lock` are NB-N's).
- **Linux:** the freedesktop notification service through `zbus` (already in `Cargo.lock` through `ashpd`), via `notify-rust` or a direct `org.freedesktop.Notifications` call; a click is the `ActionInvoked` signal (`default` action). No bundle or `.desktop` file is needed for the notification to appear; an app name and icon name are strings.
- **Windows:** WinRT toast notifications need an Application User Model ID for an unpackaged app. Candidate: register an AUMID under `HKCU\Software\Classes\AppUserModelId\<id>` at start (a display name only) and send the toast with it, which shows the toast under that name without a Start-menu shortcut on current Windows 10/11 (to be confirmed by S0.7 on a real machine); click activation of an unpackaged app is the weak point and is judged there.
- **`Platform` contract (task 6.0).** NB-B/NB-N define `Platform { badge: Box<dyn DockBadge>, notifier: Option<Box<dyn Notifier>> }` and an `Alerts` that reads the badge unconditionally. On Linux (and on Windows before XP-B) there is a notifier and no badge, so **this change owns the modification**: `badge` becomes `Option<Box<dyn DockBadge>>`; `Alerts` handles `None` by not computing or setting a label (the store's `badge_count` is not read for it) and leaves notifications untouched; `dock::badge()` and the macOS registration in `main.rs` wrap the existing value in `Some`; the NB-B fake and every `Platform` literal (found with `lsp` references) are updated. It is done in XP-N (6.0), after NB-N is on `main` (rule 1: `alerts.rs`, `main.rs`, `tests.rs` are NB-N's until then), so the `None` has its first consumer in the same unit: the Linux `Platform { badge: None, notifier: ... }` of 6.1. It is **not** requested from NB-N, which keeps its contract and its macOS-only scope. XP-N therefore builds and merges before XP-B with no stub and no no-op. Tests (`alerts.rs`, `tests.rs`): with `badge: None` and a notifier an incoming message in a background window is shown and the store is not asked for a badge count; with `badge: Some` and `notifier: None` the badge moves as today; with both `None` the entity is inert; macOS behaviour and the existing assertions are unchanged.
- **Badge on Windows (XP-B, optional, Q5).** `ITaskbarList3::SetOverlayIcon` with a number rendered into an icon. It needs the window's `HWND`, which `DockBadge::set(label)` does not receive; the trait is widened by one step to take the window handle (all implementations and the fake updated, `lsp` references first). Registered by `cfg(windows)` as `badge: Some(..)`.
- **Badge on Linux: out of scope, decided.** The only API that reaches a launcher is the Unity `com.canonical.Unity.LauncherEntry` signal `Update` for an `application://<desktop-file-id>.desktop` URI. The receiver (dash-to-dock, KDE's task manager, Ubuntu's dock) matches that URI to a **desktop entry that is installed** and to the window's `app_id`; a run from source has neither (no entry is installed, and `WindowOptions.app_id` is not set by the app today), and stock GNOME shows no badge at all. Making it work means installing a `.desktop` file and setting a matching `app_id`, which is packaging (a non-goal), and it could not be shown in the headless Linux VM: a `dbus-monitor` seeing the signal proves nothing about a launcher showing it, and the receiving side (dash-to-dock) is not available there. A claim the plan cannot verify on the receiving side is not made, so Linux gets notifications and no badge; the follow-up (desktop entry, `app_id`, the signal, a check on a real dash-to-dock or Plasma) is listed in `tasks.md`.
- The macOS badge and notifier files are not touched except for the `Some(..)` wrap of 6.0.

## Risks

- **Wayland and Windows cannot be fully checked here.** Windows has no VM; the Wayland compositor in a headless VM may differ from GNOME. Mitigation: the plan says exactly which checks are compile-only and which need the user; open question Q1 offers a CI matrix.
- **WebView2 in a helper is untested for Yandex's sign-in** (third-party cookies, 2-factor pages). It is a plain browser window, so the risk is low but real; S0.3(b).
- **GPUI on Windows is the least documented backend of the crate;** a rendering or input problem there is a GPUI 0.2.2 limitation we cannot patch (the crate is pinned); the unit XP-D ends with a Windows run that would find it.
- **Vulkan is mandatory on Linux, and GPUI fails before any handler can run.** GPUI initialises the GPU inside `Application::new()`: Wayland `BladeContext::new().expect("Unable to init GPU context")` (`wayland/client.rs:501`, a panic), X11 the same call with `?` (`x11/client.rs:414`, an error `current_platform` unwraps). So with no Vulkan loader or driver the process dies before `main` can open a window or show a hint; **the app cannot report it, and the plan does not try**. The owner is the run script, before GPUI is ever started: the preflight of task 8.5 (design D7) also checks (1) the loader: `ldconfig -p` lists `libvulkan.so.1`; (2) a driver: at least one `*.json` in `/usr/share/vulkan/icd.d`, `/etc/vulkan/icd.d`, `/usr/local/share/vulkan/icd.d` or `~/.local/share/vulkan/icd.d`, or, when `VK_DRIVER_FILES`/`VK_ICD_FILENAMES` is set, that every named file exists. A miss prints the install line (`libvulkan1 mesa-vulkan-drivers`) and exits non-zero without starting cargo. This was chosen over a probe in `main` with `ash` (a new dependency and code in the hottest file, to learn what the script already shows) and over `vulkaninfo` (a package the user would have to install to learn that a package is missing). **Limits, stated in `docs/platforms.md` and the spec:** the script checks that a loader and a driver are installed, not that a device works; an installed driver for hardware that has no Vulkan 1.1 device, or a broken one, still ends in GPUI's own terminal message (`Unable to init GPU context`) and no window, which the plan cannot improve (the crate is pinned, non-goal for older hardware); and starting the binary by hand (not through `run-linux.sh`) skips the check. S0.5 records the real text and exit status of both backends with `VK_DRIVER_FILES=/nonexistent` so the documentation quotes what GPUI prints.
- **Title bar on Linux is app-drawn** and can look foreign next to a desktop's native ones; it is limited to sessions where the compositor does not decorate.
- **Fonts:** emoji and Cyrillic depend on installed fonts; documented, not embedded.
- **Windows file-system differences** (no hard links on FAT, locked files, `remove_dir_all` of a playback folder with an open file) degrade to the atomic no-replace claim of D3, a warning, or a visible `Disk` failure, never to a lost, replaced, empty or half-written file under the final name.
- **Overlap with open work** (`tasks.md`): five open or proposed changes touch `main.rs`, `desktop.rs`, `tests.rs`, `Cargo.toml`, `Cargo.lock`; the plan keeps every hunk of this change small and sequences it by rule 1; every future binding or modifier check must follow the contract of D5 (`secondary-`), which `add-text-selection-and-quotes` already does.
- **Dependency growth:** about a dozen new crates on Linux and Windows only; each with its licence line; `ropus` is young (BSD-3-Clause, bit-exactness claimed and measured on 17 files only).
