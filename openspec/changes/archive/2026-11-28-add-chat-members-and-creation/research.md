1. **Вывод:** для управления чатами протокол в основном HTTP Registry; создание, изменение состава/ролей и продление приглашений — изменяющие операции. Профиль доступен через `whoami`; отдельный `get_current_user_data` не работает. [Проверено по описанию протокола; живые изменения аккаунта не выполнялись.]
2. **Уже есть:** HTTP-клиент с CSRF, чтение пользователей, Xiva `push` и безопасный allowlist запросов; модель чатов хранит только сводку, модель пользователя — только данные для отображения. Управления участниками, ролями, приглашениями, профилем и статусами нет.
3. **Предлагаемое разделение:** (а) чтение участников/профиля и создание личных/групповых чатов; (б) управление участниками, ролями и приглашениями; (в) изменение профиля и статусов — только после отдельного подтверждения семантики, прав и побочных эффектов.
4. **Рекомендации:** начинать с чтения участников и `whoami`; создание чата включать отдельным явным действием. Для удаления участников, смены ролей и ротации ссылок требовать подтверждение; не повторять конфликтные операции без понимания `version` и результата.
5. **Риски:** неофициальный протокол, оптимистическая конкуренция по `version`, возможное необратимое исключение участников или отзыв ссылок. Отчёт должен быть в `local://research-5.md`; доступный набор инструментов не предоставляет записи в локальные артефакты/файлы, поэтому содержимое отчёта и источники ниже переданы для сохранения главным агентом.

**Источники и подтверждённые/выведенные факты**
- `[Проверено по источнику]` Веб-клиент разделяет Xiva WebSocket и HTTP Registry; Registry охватывает управление чатами. Registry — POST с multipart-полем `request`, содержащим `{method, params}`; мутирующим HTTP-запросам нужен CSRF-токен. Источник: [`docs/protocol-research.md`, §§1, 3.1](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).
- `[Проверено по источнику]` Каталог управления включает `create_chat`, `create_private_chat`, `set_chat_info`, `change_chat_members`, `change_chat_role`, `change_chat_admins`, `leave`, `invite`, `invite_renew`; изменения могут повторяться с увеличенным `version` после конфликта. Конкретные параметры ряда операций описаны как opaque, то есть контракт недостаточно определён для безопасной реализации. Источник: [`docs/protocol-research.md`, §§3.2, 10, строки 620–655](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).
- `[Проверено по источнику]` `get_chat_members` и `get_group_members` возвращают пользователей, группы и отделы; для группового чата сведения могут включать администраторскую роль. `create_private_chat` принимает `guid`, `wait_for_update`, `onetime_user_token`; `create_chat` имеет непрозрачные параметры. Источник: [`docs/protocol-research.md`, §§3.2, 7, 10](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).
- `[Проверено по источнику]` Для приглашений перечислены `invite` (`{invite}`) и `invite_renew` (чат и параметры, включая `version`); чтение группового чата возможно через `invite_hash`. Достаточных данных о сроке действия, правах доступа, отзыве и точном формате ответов в просмотренных разделах нет. Источник: [`docs/protocol-research.md`, §§3.2, 7, 10](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).
- `[Проверено по источнику]` Профиль текущего пользователя доступен в WS-ответе `whoami` (`UserInfo`, `UserStatusInfo`); `get_current_user_data` отвергается сервером как `No such path`. Событие `UserStatus` обозначено как availability/status, но просмотренный каталог не определяет безопасный формат изменения. Источник: [`docs/protocol-research.md`, §§2.5, 9, 17.6](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).
- `[Вывод из локального кода]` Текущий код намеренно не допускает эти операции: `ReadRequest` разрешает только `request_user`, `get_users_data`, `history`, `subscribe`; `WriteRequest` выражает отправку/редактирование/удаление сообщений, отметку прочтения и typing. Новый метод нельзя безопасно добавить до выяснения payload, CSRF и обработки ошибок/конфликтов.
- `[Вывод из локального кода]` Данные пользователя `WireUser` ограничены GUID, отображаемым именем, аватаром и UID; доменная модель не содержит профиля аккаунта, состава участников, ролей или приглашений. Событие статуса профиля не декодируется как управляемое событие.

**Открытые решения и риски**
- Рекомендуемый первый объём: чтение профиля через `whoami` и состава участников; затем создание чатов отдельной задачей после фиксации payload и обработки результатов. Компромисс: полезное управление откладывается, зато действия, создающие серверное состояние, не смешиваются с чтением.
- Создание группы должно явно показывать выбранных участников и название до отправки; повтор после сетевого сбоя может создать дубликат, если у метода нет идемпотентного ключа.
- Смену ролей, удаление участников и обновление ссылок делать отдельными подтверждаемыми действиями; оптимистические `version`-конфликты требуют перечитать состояние, а не слепо повторять запрос.
- Отдельно определить, что означает «статус»: профильное сообщение/availability, online-presence или оба. Heartbeat уже упомянут как presence-событие, но изменение может влиять на видимость пользователя и другие устройства.
- Не выполнять операции над реальным аккаунтом без явного одобрения; исключение участника, отзыв/ротация ссылки и изменения профиля способны повлиять на других пользователей.
