# Исследование: change 2 — медиа

## 1. Факты протокола

- **[Проверено в локальном коде]** `FileInfo` несёт `Id2`, `Name`, `Size`, а в wire-модели локального клиента — только `id`, `name`, `size`. Комментарий указывает, что `Id2` — единственный handle скачивания: [`crates/yandex-proto/src/wire.rs:57-66`](crates/yandex-proto/src/wire.rs:57-66). `WireImage` дополнительно несёт размеры и флаг анимации.
- **[Проверено в локальном коде]** Парсер различает `Image`, `MiscFile`, `Gallery` и `Voice`; у голосового сообщения сохраняет duration. Галерея хранит несколько изображений на уровне wire: [`crates/yandex-proto/src/wire.rs:315-340`](crates/yandex-proto/src/wire.rs:315-340).
- **[Проверено по референсу, не является официальной документацией]** `FileInfo` в исследованном протоколе содержит также `Source` (MDS/DISK). Для загрузки через Disk указана цепочка `upload_to_disk` → HTTP PUT сырых байтов → `add_files`; в результате получают `file_id`, который включают в payload сообщения. Описаны также прямые upload URL для файлов и голоса. Источник: [protocol-research.md, §12.1 и §12.4](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md#12-файлы-медиа-вложения).
- **[Проверено по референсу]** Описаны URL для thumbnail/original, скачивания файла, voice playback и video streams; файлы и голос требуют авторизованной сессии. Хосты и шаблоны извлечены из runtime config, поэтому их нельзя считать стабильным публичным API. Источник: [protocol-research.md, §12.2](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md#12-файлы-медиа-вложения).
- **[Проверено по референсу]** `Gallery` содержит массив изображений; у voice есть файл и duration. `MiscFile` может включать `VideoPreview` с размерами, длительностью и blurhash. Источник: [protocol-research.md, §11.1 и §12.4](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md#11-типы-тел-сообщений-clientmessage-полные-схемы).
- **[Проверено по референсу]** `get_media_messages` предоставляет типизированный просмотр медиа с курсорной пагинацией. Источник: [protocol-research.md, §12.3](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md#12-файлы-медиа-вложения).
- **[Проверено по референсу]** В проекте-источнике есть отдельная функция извлечения вложений как ссылок; скачивание намеренно отделено от чтения сообщений: [attachmentRefs.ts](https://github.com/conarti/yandex-messenger-mcp/blob/main/src/protocol/attachmentRefs.ts). **[Вывод]** Разумный UX по умолчанию — скачивать только по явному действию, а не при открытии истории.
- **[Проверено по референсу]** Референс описывает upload flow как reverse-engineered; это не подтверждение стабильности или официальной поддержки API. См. [protocol-research.md](https://github.com/conarti/yandex-messenger-mcp/blob/main/docs/protocol-research.md).

## 2. Что уже есть и чего не хватает

- `crates/yandex-proto/src/media.rs`: `MediaConfig` содержит files/avatars base URL; `MediaTarget` поддерживает только `Avatar` и `Thumbnail`. Формируются URL аватара и `file_shortterm/{id}?size=MIDDLE2048`. `MediaClient::fetch` делает GET с cookie только для подходящего хоста, обрабатывает 401/404 и потоково ограничивает ответ 25 MiB. **Загрузки, original download и отдельные цели File/Voice/Video нет.**
- `crates/yandex-proto/src/client.rs:94-95`: фасад отдаёт `fetch_media`; API для upload отсутствует.
- `crates/chat-core/src/model.rs:22-26,74-77`: есть `MediaKind::{Avatar,Thumbnail,File}` и `MessageBody::{Image,File}`, но нет галереи, voice/video playback metadata или playback state.
- `crates/desktop/src/yandex_backend.rs:151-159,365-385`: backend переводит Image в Thumbnail; File превращает в карточку; скачивание `MediaKind::File` отклоняет как неподдерживаемое. Галерея сводится к **первому** элементу, а voice становится `Unsupported`.
- `crates/desktop/src/store.rs:380-405`: автоматически запрашиваются аватары и image thumbnails; File игнорируется. `crates/chat-core/src/cache.rs:45-46,85-89,263-279` индексирует скачанную медиа по kind/id. `crates/chat-core/src/client.rs:22-23` ограничивает параллельные media fetch четырьмя задачами.
- `crates/desktop/src/timeline.rs:230-303`: UI показывает thumbnail и карточку файла, но карточка не загружает файл; плеера и галерейного viewer нет.
- **[Проверено]** Текущая спецификация истории прямо ограничивает scope превью изображений/карточками файлов и исключает открытие/скачивание файлов: [archived message-history spec](openspec/changes/archive/2026-11-23-add-read-only-client/specs/message-history/spec.md:32-45).

## 3. Рекомендуемое разделение scope

Один change, включающий upload, download, галереи и два вида playback, будет чрезмерно связан с новыми wire-моделями, файловой системой и UI. Рекомендую:

1. **Скачивание и просмотр вложений:** file download с явным действием пользователя; полноценная gallery-модель и просмотр всех изображений; безопасное сохранение/локальный кэш. Загрузку не включать.
2. **Upload и отправка медиа:** image/file selection, disk upload flow и отправка соответствующих message payload. Реализовывать после подтверждения всех необходимых параметров протокола.
3. **Voice/video playback:** отдельный scope после подтверждения корректных URL, аудио/видео форматов и локальной поддержки GPUI/macOS. Включить voice waveform/metadata только если это нужно выбранному UX.

## 4. Решения, которые должен принять пользователь

- **Скачивание:** явная команда «Скачать» или автоматическое сохранение? Рекомендуется явное действие; оно уменьшает непреднамеренную загрузку приватных файлов и расход места, но требует дополнительного шага.
- **Место и политика перезаписи:** папка загрузок или внутренний account cache? Рекомендуются загрузки в папку пользователя и запрет перезаписи существующего файла; cache оставить для превью.
- **Отправка:** ограничиться image/file или включить voice upload сразу? Рекомендуется сначала image/file: у них описан общий Disk flow, а для voice отдельный URL и payload.
- **Галерея:** сетка в сообщении с отдельным просмотрщиком или только последовательная лента? Рекомендуются grid + viewer; это сохраняет все элементы и соответствует самостоятельному типу Gallery в wire.
- **Автовоспроизведение:** запускать voice/video автоматически? Рекомендуется только по явному нажатию, с учётом приватности и нежелательного воспроизведения.
- **Размеры и типы:** какие максимальные размеры, форматы, длительности и поведение при неподдерживаемом файле? Лимит 25 MiB сейчас задан для media GET в `media.rs`, но не подтверждён как правильный лимит файлов/видео.

## 5. Риски

- Протокол неофициальный и reverse-engineered; URL-шаблоны и upload RPC могут измениться.
- Upload создаёт серверный объект до отправки сообщения: сбой между загрузкой и `push` может оставить неиспользуемый файл. **[Вывод]** Нельзя обещать откат/удаление, пока для него не исследован и не проверен протокол.
- Отправка вложения — реальное изменение аккаунта и потенциальная публикация в неверный чат. Нужны явное действие пользователя и понятное отображение чата/файла перед отправкой.
- Download может раскрыть/сохранить приватные данные на диске и занять значительное место; не следует скачивать все вложения при загрузке истории.
- Видео/аудио требуют проверки форматов, потоковой поддержки и URL-авторизации; обычный GET с текущей thumbnail-целью этого не решает.
