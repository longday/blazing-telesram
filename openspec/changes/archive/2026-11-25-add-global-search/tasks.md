# Tasks

Each task owns the files it names and may be done in a separate session. Dependencies are explicit (`needs`); tasks without `needs` start immediately. Chains that can run side by side: **1.x** (yandex-proto), **2.x** (chat-core) and then **3.x** (desktop). Shared files (`model.rs`, `backend.rs`, `client.rs`, `yandex_backend.rs`, `store.rs`, `desktop.rs`, `tests.rs`, `request.rs`, `bt-probe.rs`) are also touched by other open changes: pull before editing, keep the diff additive.

**Merge units (every merge to `main` must compile with no stubs, no no-op arms and no `dead_code` warning; the project builds with 0 warnings).** 2.1 adds a required `Backend::search`, new `Command`/`ClientEvent` variants and a no-op engine arm; the only `Backend` impl (`yandex_backend.rs`, 3.1) and the exhaustive `ClientEvent` match in `store.rs` (3.2) are outside it, so `desktop` does not compile on 2.1 alone; the store's `search`/`cancel_search`/`search_state` and the view model of 3.3 have no caller until 3.4. Therefore: (a) **1.2, 1.3, 1.4** touch only `yandex-proto` and merged to `main` one by one; (b) **2.1, 2.2, 3.1, 3.2, 3.3, 3.4 are one unit (GS-A)** developed on the branch `integ/gs` (each task branches from `integ/gs` and is merged back into it by the Integrator; 2.1 is a saved patch to be re-applied on top of `main`) and merged to `main` together once `cargo check --workspace --all-targets` is green with 0 warnings and `cargo test --workspace` passes; it starts when the core lane is free of other in-flight units (MD-C); (c) 4.1 is a verification task. Order inside the unit: 2.1 → 2.2 ‖ 3.1 → 3.2 → 3.3 → 3.4.

(5) Typing a word within the debounce: exactly one request in three runs plus one more at the fastest speed. (6) Network off in the VM: the connection banner shows "Подключение…", a new query of 2+ characters makes no request and shows "Для поиска по серверу нужно подключение" while the local name match still filters; stale hits of the previous query stay below it (spec "Search states"); with the network back, the pending query ran by itself and showed its result. (7) `BT_LOG=debug`: `registry exchange … call=search status=200 elapsed_ms=…` and `search mapped chats/people/messages/skipped`, no query or hit text.
  - Read markers: while typing and on results nothing is reported; after a click the open-chat flow loads the history and then attempts one `seen` for that chat (blocked by `BT_WRITE_ONLY_CHAT`, so it is logged as `write blocked … kind=seen`), the same as opening the chat from the list, with the window focused and the newest message visible. Not run by hand: opening a result with an unfocused window or with the newest message out of view.
  - Observations, no defect: the server returns message hits only for some known words (several words from loaded messages gave 0 messages while others gave hits); a person whose private chat also matches by name appears in the local rows and in "Люди" (only chats are de-duplicated by spec); a message hit opens the chat at its newest messages, not at the found message (follow-up of the proposal); in the VM, keystrokes sent about 160 ms apart produced two requests twice (≈430 ms apart, consistent with a stall longer than the 300 ms pause), while faster bursts gave one. Tooling: the VM's `type.js` sends key code 0 and gpui ignores the Unicode string, so queries were entered through the clipboard (`pbcopy` with `LANG=en_US.UTF-8`, then Cmd+V) and Latin keys with real key codes; Cmd-flagged events leave the modifier stuck unless the next event sets flags to 0.
