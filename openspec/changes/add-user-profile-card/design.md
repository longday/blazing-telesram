# Design

## Context

See `proposal.md` (Why, Decisions) and `specs/user-card/spec.md` for what is promised. This section is the grounding in the code and fixtures at `main` `215b9e3` (code unchanged since `870e584`; `chat-members` and `chat-creation` are main specs since the CM archive), with what is observed and what is not.

**Where a person appears and what the click does today**
- Timeline (`timeline.rs`, `message_row`): in a **group** chat only, for messages that are not outgoing, an avatar (`msg-<ts>-avatar`) beside the last message of a run (`group_end`) and an author name (`msg-<ts>-author`, «Неизвестный» when unnamed) at the start of a run (`group_start`). Neither has a click handler. Private chats and channels show neither. The message author is `Message { author: UserId, author_name, author_avatar }`; `author` is `UserId("")` when the sender carried no guid (`yandex_backend.rs` `unwrap_or_default()`).
- Info panel (`info_panel.rs`, `member_row`): avatar, name, «админ» marker, «Написать» (`open_new_chat(Some(user))`, absent on the current user's row `member.me`). The row itself has no click.
- Chat header (`desktop.rs`, `chat_pane`): one click target, the whole header, toggles the info panel. A private chat's panel is answered from the chat row (`ChatSummary.partner`, `private_members`), so it shows one row.
- Own profile: `profile.rs` (modal over the chat; `body(state, connection)` is a pure function of `ProfileState`), opened from the account menu (`Desktop::open_profile`), `Command::LoadProfile` → `Backend::profile` → `Client::whoami()` (socket `whoami` with the **session's own** guid).

**What the wire gives about another person** (sources: `crates/yandex-proto`, the fixtures, and `add-chat-members-and-creation` `design.md` "Observed shapes", live 2026-11-24 and 2026-11-27)
- `get_users_data` (registry, no CSRF, already on the allowlist): `parse_users` reads `guid`, `display_name` (else `public_name`), `avatar_id`, `uid` into `WireUser`; the adapter keeps them in an in-memory map (`users`, filled by `Users::load`). The only other key seen in a live reply is `contacts[{type: "email", value}]` (the creation research read it to confirm a guid). `tests/fixtures/research-users.json` is a hand-made four-key fixture, not a capture. **The full key set of this reply is unobserved.**
- `get_chat_members` user (live, 353 users): always `account_category`, `display_name`, `guid`, `public_name`, `registration_status`, `role`, `version`; sometimes `avatar_id`, `contacts[] {default, organization_id, type: "email", value}` (327), `employee_info {deleted?, department {id, name}, display_name, is_admin, organization_id, position}` and `employees_info[]` (306), `gender`, `is_connect` (305), `phone_id` (127); rarely `account_type`, `email`, `is_onboarded`, `mcrm_registration_ts`, `nickname`, `uid`, `account_deleted` (1). `WireMember` models only name, avatar, role, deleted.
- `create_private_chat` reply `user` object: `guid, display_name, public_name, registration_status, version, account_category, is_connect, contacts[], employees_info[], employee_info` (the same record shape).
- `whoami` (socket): documented as `{Guid} -> {UserInfo, UserStatusInfo, CurrentTime}`; the client only sends its own guid. Own reply: `UserInfo` (`AvatarId`, `DisplayName`, `Email`, `Gender`, `Guid`, `IsConnect`, `Nickname`, `OrganizationInfos[]`, `PublicName`, ...), `UserStatusInfo { Timestamp, UserStatus: {} }`; a populated `UserStatus` was never seen (`parse_profile` reads only `CustomStatus.Text`, a path known statically). **Whether `whoami` answers for another guid is unobserved.**
- Search `users_pvp` hits: `guid`, `display_name`/`public_name`, `avatar_id` parsed; the set is usually empty.
- `docs/` holds only `mockups/` and `vm.md`; there is no protocol document in the tree (the reference cited by earlier changes lives with their `research.md`). The mockups have no user card; `docs/mockups/3-info.svg` shows the info panel whose rows become click targets.
- Allowlist: `ALLOWED_METHODS` has eight names; `Whoami { guid }` and `GetUsersData { guids }` already exist, so the card needs **no new variant** unless research R1 says otherwise. The exact-list tests in `request.rs` and `write.rs` pin the names.

## Goals / Non-Goals

**Goals:** one card, three entry surfaces, fed by one read that composes allowed methods; memory only; a pure view function testable like `profile::body`; no change to an archived behaviour.

**Non-Goals:** everything under `proposal.md` Non-goals; caching card data; a shared "people directory" abstraction (the adapter's `users` map stays name/avatar only).

## Decisions

### D1. Domain types
`chat-core::model`:
```rust
/// Another person (or the account itself) as the server describes them. Memory only.
pub struct UserCard {
    pub user: UserId,
    pub name: Option<String>,
    pub avatar: Option<MediaRef>,
    pub status_text: Option<String>, // non-blank only
    pub position: Option<String>,
    pub department: Option<String>,
    pub email: Option<String>,
    pub nickname: Option<String>,
    pub deleted: bool,               // account_deleted
    pub me: bool,                    // set by the backend, which knows the own guid
}
```
`Command::LoadUserCard { user: UserId, request: u64 }`; `ClientEvent::UserCard { request: u64, card: UserCard }`, `ClientEvent::UserCardMissing { user: UserId, request: u64 }` (the server has no record), `ClientEvent::UserCardFailed { user: UserId, request: u64, reason: String, offline: bool }`; `request` is the store's token, copied into every outcome (D4, D5). `Backend::user_card(&UserId) -> Result<Option<UserCard>, BackendError>` (`None` = no record; shaped like `message_preview`). Alternative rejected: reusing `Member` (carries a role and `me` for a list, no details) or growing `Profile` (the own account's type; its `LoadProfile` is a one-slot state the account menu owns).

### D2. Wire and sources
- `wire.rs`: `WireUserCard { guid, display_name, avatar_id, status_text, position, department, email, nickname, deleted }` and `parse_user_card(data: &Json, guid: &str) -> Result<Option<WireUserCard>, ProtoError>`: from the `users` array of a `get_users_data` reply, the entry whose `guid` equals the asked one (other entries ignored; none → `Ok(None)`); `Err` only when the reply has no `users` array (as `parse_users`). Picking rules (D3). `status_text` is filled by the caller from `parse_profile` of the `whoami` reply when D2b applies.
- `registry.rs`/`client.rs`: `Client::user_card(&self, guid) -> Result<Option<WireUserCard>, ProtoError>` sends `ReadRequest::GetUsersData { guids: vec![guid] }` through the existing `RegistryClient::execute` (no CSRF, bare cookie) and parses with `parse_user_card`. The existing `users()` and `parse_users` stay unchanged for the adapter's name cache.
- **D2b, the status text (gate G1, research R1 Q2).** If `whoami` answers for another guid with that user's `UserStatusInfo`, `Client::user_status(guid)` sends `ReadRequest::Whoami { guid }` (the variant is unchanged: it already carries any guid; `Client::whoami()` becomes a call with the own guid), reads the status by the same path as the own profile (`parse_profile`), and **takes it only when the reply's `UserInfo.Guid` equals the asked guid**: a reply that is the caller's own record, or another person's, yields no status. The two reads run **concurrently**, and a failure of the status read alone leaves the card without a status line (it is a decoration, like names in `Users::load`), whereas a failure of the record read fails the card. If R1 shows `whoami` refused, or answering with the caller's own record whatever the guid, D2b is dropped: no status line, no `Client::user_status`, and the status requirement/scenarios are removed from the spec by task 0.4. If a payload for a status is not observable at all (no account has one, as for the own profile today), the parser still reads the statically known path and the scenario is covered by a fixture only; 0.4 says so in the spec's status requirement.
- **D2c, a new method (gate G2, R1 Q4).** Only if the static reading of the web client shows it fills its person card with a method that is neither of the two above **and** the method is a read by name and by evidence (a `get_*`/`list_*` form; no write verb; observed answering without side effect), it becomes one new `ReadRequest` variant with its entry in `ALLOWED_METHODS`; the exact-list tests in `request.rs`/`write.rs`/`manage.rs` are extended by that one name, not loosened; `request.rs` then has one more owner (rule 1) and the unit takes a task 1.0. If it is not clear that it is a read, it is not added and the card uses D2/D2b only, with the gap reported.

### D3. Field rules (a pure function, tested on fixtures)
- Name: `display_name`, else `public_name`; blank counts as absent. Avatar: `avatar_id`, empty counts as absent.
- Email: among `contacts[]` entries with `type == "email"`, the one with `default == true`, else the first; else the top-level `email`; trimmed, blank counts as absent. Other `type` values (phones, if R1 finds any) are not read.
- Position and department: the object `employee_info` (the server's current employment), else the first of `employees_info[]`; `position` and `department.name`, each non-blank only. No organisation name, no `is_admin`.
- Nickname: `nickname`, non-blank only.
- Deleted: `account_deleted == true`. `employee_info.deleted` is a per-organisation flag and is **not** an account deletion.
- Everything else in the record is ignored (not copied into a type, not logged): `gender`, `is_connect`, `account_category`, `registration_status`, `phone_id`, `version`, `uid`.
- Text is shown verbatim (no case change, no link detection); the card truncates long values with an ellipsis in the view, never in the data, and the copy action copies the whole value.

### D4. Engine (`chat-core/src/client.rs`)
`Command::LoadUserCard { user, request }`: a plain read, never queued, never cached, never persisted, **never deduplicated** (as `load_reactors`: the store tells answers apart by `request`, which the engine echoes unchanged on every outcome, refusals included, and never interprets; there is no in-flight set, which is what would swallow a second request for the same person). Offline answers at once with `UserCardFailed { offline: true, reason: OFFLINE_REASON, request }` and sends nothing. `Ok(Some)` → `UserCard { request, card }`; `Ok(None)` → `UserCardMissing { user, request }`; `SessionExpired` → `expire()`; any other error → `UserCardFailed { user, request, reason: read_failure_reason(error), offline: matches!(error, Network) }` with `tracing::warn!(kind = error_kind(&error), ...)` only. `debug` logs carry the outcome and the number of non-empty fields, never a field (D9).

### D5. Store (`desktop/src/store.rs`)
One card at a time: `user_card: Option<UserCardView { seed, state, generation }>` with `seed: UserCardSeed { user, name, avatar }` (what the opening surface knew) and `state: UserCardState { Loading, Ready(UserCard), Missing, Failed { reason, offline } }`. Every send takes a fresh token from the store's `next_request` counter (the reactors precedent, `request_reactors`: it only grows, so close and reopen never reuse a token): `open_user_card(seed, cx)` replaces any view, sets `Loading`, sets `generation`, sends `Command::LoadUserCard { user, request: generation }`, asks `want_media` for the seed's avatar; `reload_user_card` (retry, and the reconnect read below) sets `Loading` with a new `generation` and sends again; `close_user_card` drops the view. An outcome applies only when the open view's `user` equals the outcome's `user`, `generation` equals its `request`, **and** the state is `Loading` (the `awaited_*` check of `finish_reactors`); anything else is ignored. So "open A, close before the reply, reopen A" sends a second request (nothing is swallowed) and the first reply, whichever order they arrive in, is dropped; "another card while one is loading" is the same check. **Reconnect:** `Desktop::resume_reads` (the existing hook called when the connection comes back, which reloads members and the profile) also reloads the card when its state is `Loading`, `Ready` or `Failed { offline: true }`; the fresh token supersedes a read that was in flight across the drop, so no store-side "stale after reconnect" flag is needed. Sign-out and account switch clear the view (`self.profile = None` is the precedent at `store.rs:395`). A `Ready` card asks `want_media` for the server's avatar. `StoreEvent::UserCard` is emitted on every change (a new variant: `lsp` references and every `match` on `StoreEvent` are updated in the same task).

### D6. View (`desktop/src/user_card.rs`, new) and `Desktop`
`body(state, connection) -> Body` is a pure function like `profile::body`: `Loading`, `Offline`, `Failed(reason)`, `NotFound`, `Ready { name, status, position, department, email, nickname, deleted, me }`; a `Ready` card gives way to `Offline` while the connection is not `Online`, and a late `Ready` is not shown (the profile rule, verbatim). Layout (modal, 380 px, the shell of `profile.rs`, but with the person's name block instead of a «Профиль» title):
```
[ avatar 96 ]
Имя Фамилия                      (user-card-name)
статус (muted)                   (user-card-status)
Должность   <position>           (user-card-position)
Отдел       <department>         (user-card-department)
Почта       <email>  [Копировать]   (user-card-email, user-card-copy-email)
Ник         <nickname>           (user-card-nickname)
------------------------------------------------
[Копировать ID]        [Написать]  [Закрыть]
```
Seed name and avatar are drawn in every state; `Loading` adds `user-card-loading` «Загрузка…», `Offline` `user-card-offline` «Сведения недоступны без сети» + retry, `Failed` `user-card-error` «Не удалось загрузить сведения» + `user-card-error-reason` + retry, `NotFound` `user-card-notfound` «Пользователь не найден» + retry, deleted `user-card-deleted` «Аккаунт удалён». «Написать» (`user-card-write`) only in `Ready` with `!me && !deleted`; «Копировать почту» (`user-card-copy-email`) only when an email is shown; «Копировать ID» (`user-card-copy-id`) in every state. Selectors also: `user-card`, `user-card-avatar`, `user-card-retry`, `user-card-close`. Labels are the Russian strings above.
`Desktop`: a field `user_card: bool`-style flag mirrors `profile` (`open_user_card(seed, cx)`, `close_user_card`, `reload_user_card`, `sync` on session end, `Escape` next to the `self.profile` arm in `desktop/composer.rs:551`); `blocked()` counts it, so no second modal opens over it; `open_user_card` closes the message menu and the reactors list as `open_profile` does and is ignored while something else covers the chat. «Написать» calls `close_user_card` then `open_new_chat(Some(user))` (D8).

### D7. Entry points
- Timeline (`timeline.rs`): the avatar element and the author-name element get `.id(..)`, `cursor_pointer` and `on_click` → `desktop.update(.., open_user_card(seed))` through the `RowContext.desktop` weak handle that the row already has; nothing is added when `m.author.0.is_empty()`; the seed is `{ m.author, m.author_name, m.author_avatar }`. In normal mode the handler calls `cx.stop_propagation()` so the row's other handlers do not see it. **In message selection mode** (`add-text-selection-and-quotes`, `message-selection` "Choose messages": a left click on a message row toggles it and acts on nothing under the pointer) the handler does **nothing and does not stop propagation**, so the row's toggle runs and no card opens; it asks the mode's predicate on `Desktop`, whose name the select change's task fixes. That predicate does not exist on `main` yet, so task 5.2 is gated on the selection mode being on `main` (or on the select change being withdrawn, which removes the scenario "Message selection mode" from the spec) and tests the avatar and the name in both modes. The bubble keeps its right-click menu and its text selection; the avatar is outside the bubble, and the name is a child of the bubble, so the selection code must keep the name label out of its hit area (D10).
- Info panel (`info_panel.rs`): the avatar+name container of `member_row` becomes the click target (`member-<guid>-name` new selector wraps the name; the avatar keeps `member-<guid>-avatar`); «Написать» keeps its handler and stops propagation so one click is one action. Seed from the `Member`. `chat-members` "Chat info panel" is MODIFIED for the row click and the header exception (`specs/chat-members/spec.md`).
- Header (`desktop.rs`): the header avatar becomes a `Stateful` with its own `on_click` that stops propagation and opens the card for `summary.partner` of a `ChatKind::Private` chat (seed: partner id, the chat title, the chat avatar: for a private chat these are the partner's name and avatar, as `private_members` already assumes). For any other chat, or a private chat without a partner, the avatar has no handler and the whole-header click behaves as today.

### D8. Actions
- Copy: `cx.write_to_clipboard(ClipboardItem::new_string(text))`, the call `desktop.rs` already uses for the log; the text is the loaded `UserCard.email` or `user` guid; no state changes, nothing logged. Tests read the clipboard back (`cx.read_from_clipboard()`).
- «Написать»: `close_user_card`, then `Desktop::open_new_chat(Some(person), cx)` with `person: Candidate { user, name, avatar }` built from the card (the server's name and avatar when loaded, else the seed's, else «Без имени»). **`open_new_chat` changes its parameter from `Option<UserId>` to `Option<Candidate>`**: today it finds the person only among `new_chat::candidates` (the partners of existing private chats and the members of the open panel, `desktop.rs:464-468`), so a person met on the timeline with no private chat and the panel closed would be lost and the dialog would open empty. With the person passed in, the dialog's `chosen` is that person whatever the lists hold (`confirm_new_chat` reads `dialog.chosen`, not the lists; `choose_person` is unchanged). The existing-chat check (`new_chat::existing_chat(person.user)`) stays first: an existing private chat is selected (verified live in CM 5.3's UI check) and the dialog does not open. A person who is the current user (`new_chat::is_current_user`, built on the `own_ids` the dialog already uses to leave the user out) is ignored: no dialog, no chosen person. The info panel row's «Написать» passes the `Member` as a `Candidate` the same way (its only existing caller, `info_panel.rs`), so both entries share one rule; `chat-creation` "Participants come from known people" is MODIFIED accordingly (`specs/chat-creation/spec.md`). The dialog's `create_private_chat` is the path CM archived **without live verification** (CM 5.1/5.3 were closed by user decision; follow-up `add-private-chat-creation-live-check`): this change neither tests it live nor changes it and does not wait on it; a failure there shows the existing `chat-creation` error state.

### D9. Privacy and logging
The card is held in `ChatStore` only, in no cache table; the adapter does not put `WireUserCard` into its `users` map (it would outlive the card). Logging follows the members/reactors precedent: `tracing::debug!(fields = n, "user card mapped")`, `warn!(kind, "user card load failed")`; no guid, name, email, status, position, department or clipboard text in any `debug`/`info`/`warn` line, and no field of the card in a panic message or `Debug` output that is logged. **What is not claimed:** `registry.rs` logs the raw body of every reply at `trace` (developer opt-in, the documented rule for every registry call), so with `trace` on, the `get_users_data` and `whoami` replies of a card are in the log; this change does not alter that and the spec says so. A unit test drives the backend mapping and the engine with a recording subscriber and asserts that no sentinel value (a distinctive name, email, position) occurs in any emitted line at `debug` or above.

## Risks / Trade-offs

- [Another user's record is partly unobserved] → research first (task 0), parsers tolerant like `parse_users`, every line optional, fixtures from observed shapes with placeholder values only.
- [`whoami` for another guid may be refused or answer with the caller's own record, and showing the caller's status on someone else's card would be a privacy-visible lie] → D2b compares the reply's `UserInfo.Guid` with the asked guid and takes the status only on a match; R1 Q2 records whether it ever matches; if not, no status line.
- [Contact details of other people appear on screen] → they are what the server already shows every member of a shared chat; memory only, no log, no cache; no export beyond the explicit copy actions.
- [Click targets collide with the select change in `timeline.rs`] → D10: separate unit 5.2, owner by start order, the name label is outside the text selection's hit area (an explicit note for that change's task).
- [One click firing two handlers (panel row + button, header avatar + header)] → each inner handler stops propagation; a test per target asserts one click causes one action and the info panel does not toggle when the header avatar is clicked.
- [«Написать» for a person with no private chat leads to the creation call that CM archived without live verification] → the `chat-creation` flow with its confirmation, unchanged; stated in the proposal; not a gate for this change. The dialog now takes the person from the card (D8), so a person outside the dialog's lists is no longer lost.
- [A guid in a message, the member list and the partner can differ in case or form] → compared as exact strings like everywhere else (`existing_chat`); no normalisation here.

## Migration Plan

Additive: new types, a new module, new click handlers. No persisted data, no schema change. Rollback is reverting the unit; the account menu profile and the info panel behave as before without it.

## Open Questions

None that change the specs or the task breakdown beyond what the research gates in D11 settle. Left for the owner and reported in the hand-off: (a) should a click on the whole private-chat header open the card instead of the one-row info panel (this design keeps the panel, avatar-only); (b) several organisations: one line pair now (Decision 3), a list later; (c) which live target(s) 0.2 uses for the shapes (reads only; a colleague, an external user, an unknown guid; no value recorded).
